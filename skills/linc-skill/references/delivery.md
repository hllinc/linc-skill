# 研发交付手册（展开）

本文件展开 SKILL.md §0 与 §2、§3：阶段门、实现入口与再入、测试先行的完整性/最小性、设计评审门、验证与收尾标签、状态同步、继续/停止判定、下线级联、外发保密、AI 能力上线、高风险韧性矩阵、重构与 ADR、跨仓与工作树、项目评估。


## 1. 阶段门与进入实现前的准备
- 每次跨阶段前逐行走"阶段入口状态清单"，每行只有拿到该门的实际产出才算满足，写个"已考虑"或指向规则的指针都不算。
- 实现前先有与任务规模相称的产品形态：用户是谁、哪个流程变化、外部可见行为、非目标、数据/权限/延迟/合规约束、验收条件、可增量发布的切片。
- 验收覆盖矩阵：每个功能点连同它触及的风险点（负向/授权/数据隔离/部分失败/幂等）都映射到一个可观察的通过/失败检查，不能只重述功能名。
- 触及服务边界、API/事件契约、数据源真相/迁移、鉴权/敏感数据、异步/幂等/重试/定时任务、发布/回滚/可观测时，实现前先过架构门。
- 架构证据必须点名上线后能运行的面：契约归属、依赖超时/密钥/发现、健康就绪、trace/日志上下文、长任务持久状态、重试幂等、回滚修复路径。
- 任何 API/RPC/事件/配置/响应信封变更，架构门必须先产出契约定义（请求响应形状、成功/错误语义、传输状态与业务码、数据位置、兼容策略、消费方、最小测试矩阵），不许客户端与服务端各自推断。
- 有用户可见面（新页面、导航、状态、权限、无障碍、可能锁死的布局或交互契约）时，实现前先完成设计就绪记录；改命令树/参数/帮助/退出码等终端面同样算用户面。
- 计划要写精确文件路径、命令、验收检查与验证期望，拆成可评审的小任务，不许出现 TBD/"处理边界情况"这类占位。
- 计划按风险缩放：低风险单文件可用简短内联计划；多文件/用户可见/跨模块/bug 修复/发布/分支 MR/风险不明的工作需显式任务拆分、验收、命令与停止条件；更大工作再补需求摘要、决策记录、测试与发布计划、已知风险。
- 计划里点名的"顺带发现的缺陷/债务/后续工作"必须带能活过计划的归属（追踪条目、状态文档条目、已接受的后继切片）或由有权者终止并引用记录，光写"记录下来了"不算跟踪。
- 高风险切片（schema/迁移、外部契约、平台运行时、鉴权、跨服务、密钥、可观测、部署）落地后先做检查点（评审 diff、解决阻塞项、更新最近的仓库文档、重跑本地门、提交）再开下一个切片。

## 2. 实现入口与再入门
- 只有读回过的、或本会话刚产出的 spec/计划/评估/issue 描述才可作为实现基线；随后检查新鲜度、范围、验收、测试、停止条件与落地状态，把结果记为入口/再入门。
- 属于其他分支/已被取代切片/别的交付的未合并计划只是存档，不能自动选中工作；用户显式选定后仍要对照真实目标的落地证据核对，已落地的条目不产生工作。
- 重启/重做进行中的交付时先找回旧设计（含 git 历史）并显式对账或取代；未经用户明确放弃就丢掉 spec 或无计划开工是交付缺陷。
- 收到光秃秃的"继续/接着做"且本会话没有已引用的活动产物时，先在真实目标上扫描（分支状态 + 同范围未落地计划/spec 文档）并记录命中与否；只存在于上下文摘要里的记录不算建立。
- 从分析转到第一次实现编辑是闸口：编辑前记录活动基线、范围、实现机制负责人（并已在会话内加载）、被触发的机制规则或"无+原因"、委派决策、可见 UI 检查点、风险清单、测试用例先行状态、每个前置门的触发/不适用结论。
- 凡是记录了负责人的字段，只能来自该负责人在本会话内实际加载与应用，凭记忆写值等于自我认证；同负责人的后续切片可引用一次加载，除非换栈、上下文压缩或规则文件变更。
- 没有边界记录就到了第一次编辑是流程缺陷：暂停、补记录、报告当前状态；收尾时未见负责人加载的切片要补事后规则审计（按触及面逐类记录应用/遗漏/不适用）。
- 激活休眠代码（打开 flag、取消注释、把孤儿函数接进真实调用方、启用被禁分支）默认视为行为变更切片；先查它为什么休眠（导入过期、契约漂移、当初就有 bug、产品/安全/紧急开关有意移除），涉及安全/权限/数据先走风险分级。
- 休眠路径的验证阶梯：mock 单测和配置检查不算证明；在隔离沙箱用脱敏数据跑真实导入与接线，导入可达只是前提，仍需行为断言、负向用例与风险匹配评审；flag 不豁免真链验证。
- 请求同时含"检查/评估/是否满足"与"对齐需求/按 spec"时，先追问权威基线在哪（除非用户已给链接、明说没文档、纯技术重构或明令只按口述）；口述基线要标注并附一行风险。
- 数值阈值要核对它绑定的业务实体维度（结果数/输入数/展示数）并比对代码里同名常量；带领域语义的回退/兜底逻辑先反查 spec 再删；给方案选项时不得凭"简单"偏好把与 spec 一致的选项标成最复杂。

## 3. 测试用例先行与完整性/最小性闭环
- 用户可见或契约可见的改动先写失败测试并确认它因正确原因失败；契约类（proto/OpenAPI/Pydantic/DDL/配置）先改契约再改代码；DB/Redis/MQ/外部依赖的测试要显式标注为基础设施依赖测试。
- 从评估转入修复前先建测试用例登记表：场景、层级、断言、数据依赖、命令、当前预期结果（fail/pass-existing/blocked/gap）、负责人；登记表建立前就开始实现的切片不能自称 TDD。
- 功能完整性与结构最小性是两个独立门：每个在范围内的验收点都要有实现面与新鲜证据，每个新增概念都要指向当前验收点或硬约束；一边通过不能抵消另一边失败。
- 从活动需求/验收源出发建"验收点→源决定→实现面→验证→新鲜证据→状态"表，保留稳定 ID；源没编号就生成 ID 并标注源修订，防止后续改写悄悄抹掉在范围内的点。
- gap/blocked/unknown 任一行阻塞 complete；out/deferred 只有产品或人的显式决定才是终态，deferred 还必须有持久的后续追踪定位，聊天消息不算；实现者不得自行缩减范围。
- 目标闭环：先固定"目标"与"成员单位"（目标说每个账户，成员就是账户而不是请求/批次/页），从目标的记录系统枚举总体并写明枚举器与过滤器，未经授权的过滤不缩小总体。
- 总体预检：满足依赖多条记录/事件/用户或持续到达即 fires；does-not-fire 必须引用独立于本次交付的权威来源；fires 时收尾前对账"枚举到的 vs 达到终态的"，差集即 gap。
- 结果类别行：正向、负向、纠正/恢复、模糊或表面成功四类必须全部列出并各自枚举可独立失败的变体（超时、拒权、校验拒绝、冲突、死信）；范围 in 而实现面 none 就是 gap。
- absent 需引用使其不可能的机制（状态机/契约/schema 约束），编辑组件外有重试/重放/人工修复/上游重投能产生该类别就不许标 absent；deferred 类别使目标处于 interim，报告写"切片完成；目标 interim"。
- 每次操作的样本/批次/时间/资源上限只是调度，不缩小总责任；开放总体或任何成员被推迟时，要有执行过的续跑证据证明游标单调推进且每个成员终会被选中，续跑假设需被观测或被他人拥有的告警监控。
- 概念增量表：抽象、间接层、模块/服务、状态实体、依赖、配置开关、泛化路径、扩展点都要写当前依据与更简单的替代并做 keep/simplify/remove 决定；"以后可能用"不是证据；已决定 simplify/remove 但 diff 里还在即阻塞。
- 删除或降级已有接口前按语料分类消费者（生产/非生产/模糊），已导出或公开的接口是独立契约语料，仓内无调用不代表无消费者，必须走弃用/版本路径。
- 只有纯内部文档 diff 可两轴 not-applicable；纯重构/机械维护只豁免功能轴、结构轴仍要概念表；触及契约、schema/迁移、权限、配额/定价、配置默认值、用户可见文案的 diff 一律不豁免；分类由评审者按 diff 确认。

## 4. 技术设计评审门
- 触发设计门的工作以"有记录的独立对抗评审"为闸：保存具体异议、处置与评审者身份；同 agent 内联评审只允许用于明确低风险、无实现 diff 的设计。
- 独立评审绑定实现 diff 而不只绑定上游设计决定；测试全绿不抵扣（测试只证明代码做了它做的事，写来锁定现状的测试可能正好锁住缺陷）。
- 纯移动提交的例外要同时满足：移动独立成 commit 且内容等价（缩进敏感文件的缩进变化算内容变化）、在该 commit 上跑过全套并核对未触及构建标签/路径发现/注册顺序等敏感面、净非移动 diff 仍做完整对抗评审、评审行绑定最终候选 SHA；"refactor-only"标签只是主张。
- 设计提出新的机械化门（CI 门、pre-commit、校验器、证据装置、迁移守卫）时必须记录作者自用验证、常规改动的边际成本、与信任模型的匹配；用重设计而非事后一轮轮加固。
- 一次落地撤回或缩窄某机制赖以存在的证据主张时，同一落地里把该机制重新落到仍成立的主张上或退役；无法同步处理的 pending 要有名字的风险负责人、正在付出的成本与结束事件。
- 独立评审前先在有修订历史的记录里持久化实现者自评行：验收重核、变更文件与范围、边界/失败路径、先红后绿的回归测试名（或不可行原因）、已跑的确定性门与各自证明、残余风险；行必须能证明先于评审存在，事后补的评审无效。
- 候选 diff 变化（增删文件或实质内容变化）后刷新自评行并全范围重跑独立评审；修复评审发现后的重跑是全量而非"确认我的修复"，作者不能自行判定"仅空白/错别字无需重跑"。
- 共享运行时的横切原语（拦截器/中间件链、日志/指标/恢复适配、上下文/身份传播、全局环境接线）是高隐藏边缘类：为传播、调用方覆盖、空输入、可选依赖失败、请求形状不对称各做一轮对抗并各补回归测试。
- 独立评审才发现基本范围/契约/隐私/测试问题即流程缺陷：修好自评与确定性门循环再重跑，但发现的问题仍需处置而非因此降级。
- 高风险资金/权限/数据路径与有外部消费者的契约变更，在实现、合并或上线前需真人/团队签字（含接口 diff 与兼容决定）；只做只读调查或不合并的一次性原型可免，提升为实现时重跑此门。
- 仅凭 spec+计划就进入触发工作的实现是流程缺陷，不是捷径。

## 5. 代码评审与反馈接收
- 评审输入限定到最小有用 diff，排除生成/第三方/依赖/大产物；空输出、超时、鉴权失败、像续写的输出一律视为不确定，记 pending 后缩窄输入重试，沉默不等于批准。
- 单 PR ≤400 行是甜点区，>800 行强烈拆分；生成/机械重构/迁移/锁文件更新经评审者同意可放行；评审者首轮响应不超过 1 个工作日。
- 每条 finding 必含位置、问题、建议方向；作者逐条回复（已修+commit / 不修+理由 / 需讨论），大评审可按主题批量但要标明哪些未解决。
- 安全：服务端校验类型/长度/格式/范围/授权；不拼接不可信输入；先鉴权再副作用；执行拒绝的代码必须就在执行副作用的操作里（工具没暴露在 schema、被 prompt 过滤或被 facade 挡住都不算拒绝）并在那里测试。
- 正确性与可靠性：空/零/负/极值/重复/畸形输入有意处理；并发写有事务/CAS/锁/幂等键/唯一约束；多步持久变更有事务或补偿；无 N+1、无界扫描/扇出/队列；依赖调用显式超时重试熔断降级；资源都关闭。
- 负空间评审：从原始验收源、验收到证据表、概念到需求表和最终 diff 一起看，只看 diff 看不出缺失行为；拒绝隐性省略与实现者自行缩范围。
- 每条"保证"分级为 strong/eventual/best-effort/unsupported；文档写"保证"而代码是尽力而为即 finding。
- "关闭开关零影响"要走六条禁用路径核实：导入/模块初始化副作用、启动注册钩子、API 面暴露、共享状态/schema、UI 入口可见性、关闭态运行路径本身。
- 模型可见的措辞就是行为：改 prompt/工具描述/工具结果/诊断文案需要快照回放或评测证据，"只是改了描述"是未评审的行为变更。
- MR 描述是证据载体：写下实际运行的验证命令与各自证明了什么，"测试都过了"是主张不是证据；接受的风险与推迟项单列并写明接受者，这是给评审者的证据而非合并授权。
- 评审输出以 finding 领头（严重度、位置、影响、修正建议），每条关键陈述标 Observed/Reported/Hypothesis，Observed 要附可审计的命令与结果，非 Observed 附验证步骤;全是 Reported/Hypothesis 的评审只是阅读摘要。
- 严重度：Critical（安全、数据完整性、契约破坏、不可逆迁移、发布阻塞）、Major（可能的生产 bug、缺事务/幂等、权限坏、缺关键测试）、Minor、Info；Critical 无修复或无显式接受风险决定不得批准。
- 接收反馈：先读完全部再动手，逐条对照代码库核实，有证据就反驳，反驳错了就基于新证据撤回并实施，不写长道歉；"你说得对/好观点"代替核实证据即失败。
- 先给 finding 分区：机械类进修复清单；质疑机制成本/可操作性/是否该存在的设计类先交风险负责人决定 keep/delete/narrow/replace 再投入加固；新增能力或抽象的建议要先回答"哪个当前验收点或硬约束需要它"，没有定位就是拒绝。
- 遇到多条相关但不清的意见、会改产品行为或公开契约、与架构/安全/数据完整性/兼容冲突、评审者可能缺上下文时，先停下确认再实现。

## 6. 验证与收尾标签
- 不做新鲜验证就不许说 complete/fixed/passing/ready：找出证明该主张的命令或检查，运行、读输出、报告实际结果；lint 通过不证明构建/测试/迁移/用户流程通过；子 agent 的成功报告不是证据。
- 深度自审是对"本交付宣称的每条属性"的逐条枚举（设计文档、注释、commit、MR 正文、测试名），为每条写出会让它失败的杀伤性变异；无可执行检查的属性记 unverified；先证明检查本身能失败（路径错、大小写、范围过窄、吞掉非零退出都会给出假干净）。
- 变异只在隔离依赖或最低层做，绝不为了买 RED 去关掉共享/在线环境的授权、幂等或删除守卫；修评审发现产生的代码与即将发送的完成消息/MR 正文同样欠一次枚举，最后一次提交晚于最终自审的交付是 interim。
- 机械门降级阶梯：优先纳入版本管理的验证脚本 + 阻塞 CI/分支保护；本地 hook 只能调用已跟踪的非破坏命令且永远不是唯一证据；无 CI 时退化为跟踪脚本 + 安装式提交钩子。
- 发布前确认：codegen/迁移/配置/部署元数据齐全；健康就绪、日志指标追踪告警覆盖改动路径；回滚或缓解已定义；回填/重放/兼容窗口有计划；异步长任务暴露可见状态、终态、超时、重试与结果指针；前端有权限/空/加载/部分/可重试错误/不可恢复错误/取消/陈旧数据/版本提示等处理。
- 自动化验证要"观察系统"而不只"走一遍"：UI 看可见状态、控制台错误、网络失败、后端日志；后端看响应契约、trace id、持久状态、发出的事件、依赖结果与指标信号；只点过路径忽略隐藏错误的"自动化通过"不接受。
- 落地证明先于读任何状态文档：远端支持的分支必须先 fetch 目标 ref 再判定，fetch 失败重试一次后报 inconclusive 并停止，不回退到本地 ref；本地分支要用提交祖先或合并提交证明；MR 待合并时对照 MR 头和新鲜目标 ref 双向对账。
- 收尾要发现所有 agent 会读的状态面（契约文件、README、仓内交接/状态文件、状态校验器、用户指向、外部追踪器、推迟项路径），每类报出引用或具体的否定证据；无法验证的"没有"是阻塞缺口。
- 应交但未闭合的真实/运行时证据记为 interim：只有非 agent 的锚点（用户原话、用户写的状态项、引用了用户批准的状态项、由用户指定归属的后续门）指名同一证据并声明其为终态时才可写 deferred-accepted；agent 自己写的状态/门/交接文本不能给自己授权。
- 命令本轮可跑却没跑是 pending 而非 deferred；本地/mock 门只有在使用不同命令且证明与被推迟运行时无关的阻塞时才算独立进展；不得因为真实证据缺失就去加固校验器/配置/测试。
- 开发者面（CLI/SDK/库/公共 API/开发者文档）以真实的发现→安装→首次成功旅程为验收证据：记录步骤、首次成功耗时、摩擦与实际报错文案；每条新手会碰到的错误都要说明问题、可能原因与修法；安全默认值保持 fail-closed，DX 不构成 --insecure 类旁路的理由；破坏性变更要有迁移路径。

## 7. 状态文档与决策记录同步
- 交付改变共享产品状态、路线图、验证状态或跨仓就绪时，代码 MR 落地后在同一批次更新归属的状态文档：评审产物链接、合并状态、流水线结果、验证命令、剩余风险；不许产品文档在实现落地后仍声称待办。
- spec/设计文档/ADR 内嵌的进度标记也是状态面，在落地实现的同一 PR 里翻转；交付前 grep 归属文档里的进度标记与 as-built 偏离并把"未发现"记为已检查结果；最好不在散文文档里嵌可变进度字段，改为指向单一追踪器。
- agent 消费的追踪器是工作本身：共享落地时进入同一变更集或编排批次，本地交回时进入同一 diff 或标 pending+负责人；RED/WIP 提交可不更新，但最终交付状态必须一致，禁止先代码后补状态。
- 合并前以及任何评审者编辑/squash/rebase/平台合并之后，按最终 diff/ref/CI 重新校验追踪器；行为变更行只有两张闭环表齐全、验收 ID 对账、无阻塞行时才 complete；状态指向最终落地 ref 而非 squash 前提交。
- 活追踪器保持紧凑：恰好一个当前状态、恰好一个下一步、只列影响下一切片的风险且各有负责人与过期时间；已关闭项移入历史；不用原始追加日志充当活追踪器。
- 多仓或改动远端分支/MR/流水线/发布/产物状态的交付要有交付状态账本：每个变更单元一行（目标分支、同步状态、产物/提交、验证状态、MR 状态、清理、残余风险、下一步）。
- 任何"全部 N 个/每个/完成"的集合性主张，先从目标本身重新扫描推导各成员的实际后态并断言"意图集合 == 覆盖集合"，循环跑过列表不证明列表完整，N 对 N-1 的计数差是信号。
- 完成态回复要把"agent 作业"与"外部异步等待"分开：每个外部等待记对象链接、分支/SHA、作业/部署/评审 id、最近已知状态与来源、下一个门或解锁动作；有 pending/running 的外部等待时不推荐合并。
- 必须不丢的决定进持久记录（ADR、稳定路径 changelog、spec 决策日志、策略级 issue/MR 永久链接）并写负责人；可被 squash 的 MR 评论不算持久。
- 上游权威的取值集不要复制进本仓，保留指针 + 读取时的修订号 + 评审者的比对结果；确需固定值就冻结进契约产物（IDL 枚举、schema、生成代码）而非散文。
- "上游对此没有规定"是关于整份文档的主张：枚举上游该主题的全部章节读完，或把结论限定到实际读过的章节；关键词命中即停是错误样本。
- 执行层文档与其上位 spec 冲突时 spec 裁决且执行文档在同一变更中修正；跨仓的修正要成为接收方已接受的可追踪条目并标注漂移开放；被替代的规则标注日期与替代指针，不静默删除。

## 8. 继续/停止判定
- 合格的下一切片来自显式状态/任务/验收源或用户的活动继续指令，且低风险、本地或已授权、在接受范围内、归属清晰、可用现有命令验证，不需要破坏性动作、外部采购/资金承诺、生产访问、法务/合规/产品战略决策或高影响架构选择。
- 停止条件按动作逐条判：显式停止、只要状态、必需门失败/待定/不确定、脏或冲突的工作树、环境修复后仍不可用、高影响决策、破坏性动作、外部付费、归属不清、同意含糊、缺更严的授权、多个可行方案无占优且可逆、无证据的投机修复、没有低风险切片。
- 检查失败时先做授权范围内的诊断与修复再决定停：引用失败输出、修复尝试（或不安全/越权的证据）与残余阻塞；一个失败判定本身不阻止诊断。
- 等待自己启动的有限命令/测试/评审不是停止条件，等它结束并在同一轮继续；常驻进程（dev server、watch、tail）取就绪信号即前进，不无限轮询；结束回合只为报告"它在跑"是过早停止。
- 每个回合结束前先说出下一步动作，能现在做就不该结束；回合只在真正需要用户（未决决策、缺授权、显式停止）的第一个动作处结束；用户问"为什么停了"是这个缺陷的复发信号。
- 下一轮先按顺序恢复意图：当前显式指令优先；短同意（ok/好/继续/👍）绑定到最近仍有效的具体提案原文并引用它，后续消息已撤回或替代的不再绑定；恢复会扩大范围或增加动作时改为 blocked 并提问。
- 多个实质不同的提案未决或范围/授权不清时只问一个针对性问题；不要让用户修标记或重复清楚的指令；标记本身不提供授权。
- 输出用 continuing:（动作与范围，并在同一轮执行，工具调用与产物才算执行）或 blocked:（动作与范围 — 具体阻塞，只索要缺失的决定或权限）；显式停止/只要状态就直接答状态且不再反复确认。
- 被阻塞的补丁/评审/落地不阻塞所有动作：可继续独立诊断、有界修复、监控已有句柄或独立的已接受工作，但独立工作不得依赖待定判定也不得修改被评估的候选；改候选的修复是补救，须等当前运行到终态再刷新证据重入门。
- 质量门失败先做保持其目的的修复（含阻塞交付的基线失败），再重跑门与受影响测试；不缩短标识符、不删必要注释、不弱化基线、不改历史来让计数器通过；无安全修复时报告证据与真正要做的决定。
- 从状态源推导下一步前先对照当前分支/MR/合并/CI/tag 状态；状态源声称未开始而实际已合并（或反之）即陈旧，先跑状态修复切片，不从陈旧源或 git log 猜下一步；需要翻历史猜下一步本身就是状态源陈旧的信号。
- 继续授权默认包含必要的修复、测试与评审，不授予合并、发布、破坏性、生产、对外发消息或高影响决策权限；用户显式的成本/轮数/停止限制优先；已配置的内部自用模型/工具账号不算外部采购。

## 9. 功能下线级联
- 功能下线、缩减或替换是多方参与的交付切片而非一行状态变更：只改产品文档而留下测试用例、自动化测试、死代码、看板、告警、开关的下线是不完整的。
- 第一步确认范围与真相来源：功能名、来源决定（产品文档/需求变更/上线复盘）、生效日期、立即还是分阶段；来源决定缺失就停下回到产品/需求，不删任何代码或测试。
- 测试用例层：受影响用例标"废弃"而非"跳过"，追加含原因与来源链接的流转记录，同步到本地镜像时标注不删行；废弃用例冻结，自动化不再改其状态。
- 测试代码层：按用例 ID 找到关联测试，用各栈的导入图命令判断业务代码是否仍被生产代码引用；代码已删或无其他调用方则在同一提交删测试；仍被引用则默认不动；多用例共用的测试只摘掉废弃 ID。
- 代码删除交给该技术栈负责人：处理器、路由、模型、UI 组件、终端命令与不再有调用方的专属资产一起删。
- 运营收尾逐项检查并记为 removed / kept with reason / not applicable：引用已删面的看板与告警、功能开关与紧急开关、定时任务、生成的 SDK/契约产物、专属 CI 门、面向客户的文档、发布说明；不许静默跳过。
- 代码删除落地后跑孤儿检测：用例 ID 已废弃或缺失的测试、以及无用例 ID 且底层代码已删的测试，按孤儿规则处置后才关闭切片。
- 同一批次更新产品/状态真相文档与共享路线图，引用合并的提交、删除的面与废弃用例 ID；代码没了文档不能还写着"活跃"或"待下线"。
- 第 2–7 步都有证据才算 complete；缺一步是发布缺陷不是后续工作。

## 10. 产物外发保密
- 交付产物（spec、计划、需求、状态回写、上线/任务卡、复盘）或由其生成的任何文本跨出本机可信边界前先做语义保密检查：共享文档/表格/外部追踪器/wiki、MR/issue 正文与评审评论、commit 信息/分支名/tag/发布说明/CI 元数据、外部模型调用或委派 worker 的 prompt。
- 只留在本机、无跨边界交接的内部临时件不触发；触发点是外发而非"每份文档"。
- 本门只管扫描器抓不到的语义敏感：与负面评价绑定的具名个人改为角色/团队；与负面事件绑定的客户/供应商匿名化；未公开的战略/路线图/内部 KPI/内部分期措辞删除或泛化或确认目的地已获批；NDA 材料阻断直到负责人明确批准；未公开的内部代号换成通用标签。
- 密钥/凭据/原始日志、PII 字段、诊断证据外贴各走各自的既有脱敏与安全评审路径，不在这里重做。
- 阻断理由、评审包、审计记录本身也是外发物：跨边界时只写"类别 + 脱敏占位 + 仅本地可用的定位"，绝不引用原始敏感片段或真名。
- 硬类别（NDA、明确机密战略发往广泛/公开目的地）不写出边界的任何位置；确认类别（具名个人/客户/代号/内部 KPI 发往需知内部目的地）脱敏后交用户决定改写/匿名/知情继续，广泛或公开目的地不提供"静默继续"。
- 阻断只停外发不停工作：草稿保留在本地工作位置，只存在于模型上下文的先存到本地再阻断；绝不删除或覆盖用户草稿来"解决"发现。
- "明确批准"= 用户/负责人对这段具体内容发往这个具体目的地的批准；ACL 成员、"这是内部频道"、全公司 wiki/MR"内部"、agent 或跨模型推断都不是批准；广泛内部、广泛共享和未知目的地按公开严格档处理。
- 一次保密知情继续只授权该次内容外发，不授权合并、自动合并、推默认分支、force-push、删除或清理。
- 通过不是"保密安全"认证：只记录考虑过的类别与采取的动作（或无触发），不输出"语义安全已通过/无机密内容"式保证。

## 11. AI/算法能力上线
- 顺序铁律：产品定义不清不进方案评审；业务效果基线不清不进研发排期；基线未达标不进上线评审；算法局部指标变好只是必要条件。
- 产品定义先答三问：给谁用哪个任务变好（只写能力名/模型名不通过）；哪个业务结果必须改善、什么不能变差（无基线/无 owner/只有离线指标不通过）；为什么现在自研/采购/迭代（默认自研无投入产出说明不通过）。
- 业务效果基线在方案评审前冻结：当前基线、最低上线标准、目标值、观察周期、统计口径、每日看数/扩量/回滚的责任人、阈值提出/确认/变更审批人；上线评审现场不得临时改标准，变更要记原因/影响/批准人。
- 基线必须含整体链路指标而非只算法局部指标，且要进入埋点、看板、实验分组、版本标识与回滚开关，否则不进测评验收。
- 新能力还必须证明自研与三方投入产出（同一时间窗与数据集，至少 6 或 12 个月口径，不只看单次调用成本）和行业/三方效果对比；迭代能力必须给老版本基线、同口径新旧对比、失败样例分析。
- 评测集至少三类且版本化：固定基准集（用于训练/微调/提示词调优过的不能当基准）、回归坏例集（线上问题与历史严重错误必入，每次发版必跑）、灰度观察集；记录版本、来源时间、样本量、标注规则、负责人，高风险项目评测集负责人与模型优化负责人分离。
- 版本可追溯：测评报告记录模型、提示词、检索/索引、知识库、工具、后处理、三方服务与配置版本；日志、埋点、看板必须能按版本归因，否则不进上线评审。
- 影响线上体验的算法变更必须多版本实验或灰度，不能直接全量替换：分流规则、版本标识、样本口径、扩量/暂停/降级/回滚阈值、高风险场景隔离提前定义；A/B 判业务效果差异、灰度控上线风险，结论不混用；不允许看到结果后再补口径与停止规则。
- 组合链路（子模块变更）必须回答改了哪一段（链路只能来自产品/技术文档、代码、配置或日志，未确认节点标"待确认"不得写成真实链路）、影响谁、怎么证明整体没变差；验收分模块级、链路级（契约/版本透传/日志/回滚）、产品级三层；无法确认真实链路不得进上线评审。
- 上线前定义监控与回滚规格：告警指标与阈值、响应时限、处置动作（暂停扩量/降级/切老版本/切三方/关入口/人工兜底）、回滚时限、工作与非工作时间授权人、回滚后的验证动作；高风险样例定义抽检比例与处理时限。
- 判定通过：核心业务指标不低于最低标准；新版本收益明确或收益/风险被评审接受；下游业务指标不变差；严重事实错误/红线误答/严重错译/严重溯源错误原则上 0 容忍且例外须在立项或方案评审书面批准；工程指标（QPS、P95/P99、首 token、成功率、超时率）与成本在线内；兜底已演练。
- 局部指标提升但整体变差不放行：识别率升而输入完成率降、召回升而可信答案率/溯源降或幻觉升、翻译指标升而可下载率/格式/状态闭环/成本变差、点击率升而成交率降。
- 上线评审只允许四种结论：允许全量、允许实验或灰度、暂缓、禁止；不接受"基本可以/问题不大/先上再看"。
- 使用三方 AI 服务、跨境传输、客户文件、行业敏感或用户隐私数据必须有安全/合规确认；缺失必备材料是 no-go，除非上线负责人在材料里记录例外范围、风险、owner 与跟进日期。
- 全量后遇模型/提示词/检索/索引/知识库/工具/三方配置变化、线上分布/无答案率/失败率/成本/坏例类型明显变化、发现严重错误、供应商条款或价格变化、核心指标连续低于标准时必须重评或重跑核心测评。

## 12. 高风险韧性门与场景矩阵
- 触发面：资金/计费/配额/积分/退款/权益/对账/审计状态；登录/权限/租户与用户隔离/隐私/敏感数据；写请求、回调、MQ 消费、定时任务、导入导出、长任务等可能重复的副作用；用户会信任的高影响 AI 输出；用户可能双击/刷新/离线/不知道是否完成的提交流；写终局性风险。
- 产品先决定什么可降级、什么必须 fail-closed、什么必须拒绝而非给出弱结果；降级/拒绝/超时/重试/客服/补偿文案由产品拥有，工程不得实现时临时发明。
- 高风险能力在生产默认关闭或 fail-closed，直到显式配置、审批与验证；本地桩与测试默认值不得暗示生产已启用。
- 高影响 AI 的可用性不能静默压过质量：回退/降级需显式的质量等价决定，否则返回明确的拒绝/降级态；资金、权限、隐私、隔离与敏感写入遇不确定即在副作用前拒绝或停止。
- 高风险路径缺租户/操作者/主体/资源范围/权益/授权上下文时不得回退到默认身份或默认租户；默认只允许显式的引导/种子/非用户面维护流程且单独审批。
- 每个 P0/P1 端点或作业有负责人、超时预算、限流/并发上限、规范错误行为、trace/request id、可观测的依赖错误。
- 写请求不自动重试，除非幂等有持久键/唯一约束/状态机/去重表等证明；仅 Redis/内存/TTL/进程内去重对资金、配额、权益、审计、外部确认或不可逆副作用不够持久，要么持久幂等要么显式标为尽力而为。
- MQ/回调/定时/导入/长任务默认假设重复投递与部分失败：需要幂等、退避重试、终态失败、修复或补偿、可见状态；降级不得绕过授权、隔离、配额、审计与留存控制。
- 资金/配额/权益/外部确认副作用必须有对账并能产出差异清单；主变更与审计/outbox 证据不能原子提交时需 outbox、补偿记录、可重放修复路径与可告警的对账缺口，变更提交后再抛错不够。
- 管理端修复/重放/隔离/忽略/重入队/结算流程需要显式 claim/complete 状态、陈旧计数、最老年龄指标、幂等键与操作者/请求/trace 证据；AI 生成的超时/限流/路由/回退/熔断运行时配置激活前需人工批准并记录理由。
- 客户端：用户必须看得到 pending/成功/失败/部分完成/排队/可重试/取消/阻塞（通用 toast 不够）；AI 或自动化生成的内容先以草稿/候选/预览/待审核态出现并带来源与状态元数据；提交防重复（禁用态、幂等键、终态轮询、服务端确认展示）；长任务刷新/重启后可恢复；失败视图暴露 request/order/task id 或客服码；降级 AI 输出可见标记且不与正常输出同貌。
- 上线前建紧凑场景矩阵（只含触发的风险类，但跳过触发类必须写理由）：重复副作用（重复提交/回调重放/MQ 重投/作业重启/刷新回退）；权限不确定（鉴权超时、缺能力、陈旧会话、跨租户不匹配）；资金/配额（双扣、部分扣、回滚退款、对账差异）；AI 失败（超时、限流、不兼容回退、弱模型未批准、无效/不安全输出）；AI 可审性；用户终局性（长时间 pending、断网、重启、部分成功、失败后重试）；事故支持（trace id、日志指标、客服解释与补偿路径）；原子性/对账；缺上下文被拒绝。
- 每个选中行必须有证据产物（命令、测试名、幂等键、持久状态、响应、审计 trace、任务 id、截图、评测报告、差异清单、告警、修复记录）；"跳过理由"空白只在该风险类未被触发时可接受。

## 13. 重构、质量专项与架构决策
- 重构与功能/修 bug 分开；先建立绿色基线（或记录基线本就失败）；小步、可评审、可独立测试；改公共函数/DTO/契约/配置键/存储字段/事件/导出助手前搜全调用点（含生成调用、测试夹具、持久历史数据、缓存、队列消息、回放输入、依赖名字/状态/错误码的看板）；根因未知时不扩大重构。
- 已发布或外部消费的契约默认兼容：不删/改名/改语义/停止接受既有字段与码，除非真人看过风险评估后明确批准；风险评估要写消费者、上线顺序、兼容窗口、迁移或双读双写、监控、回滚、用户影响与证明切换安全的测试/回放；上线状态未知按已上线处理。
- "零行为变更"要用确定性锚点证明（一致性摘要、golden 输出、差分测试）且多步重构每步都跑绿；分阶段退役旧路径时保留薄兼容垫片，让漏改的调用点在编译期失败而非静默变行为；风险遗留重构前先加特征测试。
- 被测行为当前不可达（库私有、与原生/平台/UI 纠缠）时先做最小的行为保持的可测性边界（抽纯逻辑、注入依赖/时钟/客户端、包接口），再写特征测试；不为可测而暴露密钥、权限决策、特权内部或不安全句柄；无有意义的前后检查就不称"受测试保护"。
- 遇到文件大小/复杂度门失败：读懂门的意图后按职责、内聚、调用方与依赖方向抽取连贯职责或消除真实重复，不缩短名字、不删必要说明、不堆语句、不任意拆碎、不改阈值或历史；更小的文件不等于更好的设计。
- 每次重构说出具体动因（对齐团队约定、降低认知负担、命中信息泄漏/时间分解/过度暴露/透传方法/模糊命名等反信号、浅模块、测试可达性），"不优雅"不是单独理由；优先吃掉接口与实现同体量的浅模块，不为复用抽浅模块。
- 质量专项按相位走且顺序不可跳：Phase 0 用可重复命令量化基线（热点/最大文件、静态告警数、覆盖率、CI 状态、缺陷率）并用风险分级标出高风险面、选定驱动与前后目标对；Phase 1 先止血（按变更行范围的无新增告警/覆盖不降/新文件大小触发评审，先对主干干跑再转阻塞，抑制需负责人批准，不用全局百分比覆盖门）；Phase 2 安全网（高风险面先盘点已知坏行为并修复而非冻结，其余加特征测试，锁不住的标 needs-seam 并禁入 Phase 3）；Phase 3 按变更频率×缺陷密度×业务风险×可测性排序做小步可回滚重构；Phase 4 把规则写回约定并出前后对比报告。
- 每个相位出口要命令+输出+提交+范围+负责人的证据而非文件存在；安全/权限/隐私/资金/隔离/高影响 AI 面任何回归立即暂停回滚，软信号提前定数值阈值与停止权限；每个既有项目至少保持"基线数字 + 变更行新代码门"的最低地板。
- 写 ADR 的触发：跨服务/跨团队契约、切换成本超一个 sprint 的选型锁定、6 个月以上或不可逆承诺、存在被明确拒绝的备选、非显然的权衡、多团队签字、迁移/废弃策略；命名、单文件重构、模块内部实现、可逆配置调整不写。
- ADR 最小字段：标题（名词短语）、状态、背景、决定（1–3 句）、后果（2–5 条已接受的代价）、真实考虑过的备选及其为何输（没考虑过就如实写 none-considered 及原因，重建不出写 not-recorded，不伪造）；大量比较分析放 spike 文档，ADR 只记决定与理由摘要。
- 评审见到新加数据库/缓存/队列/框架/云、公开 API/事件/鉴权流变更、schema 迁移或字段弃用、不可逆数据模型改动、跨团队决定、影响客户可见行为/SLO 的默认值变更即阻塞"需先有 ADR"，实现 PR 引用已 Accepted 的 ADR 号。
- 取代旧 ADR 必须回链、解释变化、标全量或部分取代，并在同一 PR 改两边；被否决/搁置的原文保留不删；实现与设计偏离时追加带日期的 as-built 节（只记事实、不改原文、不是批准通道），鉴权/数据保留/超时失败模式/对外契约等实质偏离无论何时发现都触发决策负责人评审，合并后发现的还必须走缓解/回滚或取代决策。
- 架构权衡用质量属性词汇具体化（功能适用性、性能效率、兼容性、可用性、可靠性、安全性、可维护性、可移植性，加部署性与可观测性）：ADR 背景声明最多 3 个优先属性，后果写让位的属性与可承受度；评审用"来源/刺激/工件/环境/响应/度量"六字段场景代替"性能要好"。
- 单体 vs 拆服务：团队小、限界上下文未稳、需要跨模块强一致事务、单节点仍能撑、联动发布常态时用模块化单体起步，并用包边界/模块级适应度函数/每模块自有 DAL/类 RPC 签名保持可拆；至少两个信号（团队扩张、上下文 6 个月稳定、发布节奏差量级、负载差量级、异构技术栈收益、故障隔离刚需）才考虑拆；上下文仍在变、需跨模块强一致、可观测基础不成熟（至少集中日志+基础指标+关联 ID+runbook）时硬停；"感觉太大/想用新框架/领导要求"不是理由；迁移按锁边界→反腐层→拆 schema→拆服务→观察决定继续或回退的小步走，每步可 ADR 可回滚。

## 14. 跨仓协同、分支与工作树
- 一个特性跨仓时只保留一个特性权威面（单特性 spec 或程序 spec 的切片节），不在多个仓同时重定义目标；跨仓契约放在栈中立的独立仓或发布产物，消费方按显式版本/兼容策略消费，生成方发布前仍过契约评审。
- 外部或不可升级的消费者（公共 SDK、移动端、合作方、缓存客户端、长活 worker）需要显式兼容窗口与弃用策略；默认指定契约管家（可阻塞、评审时限、升级路径）；触及同一契约区域的并发切片在契约处串行。
- 每仓协同状态要写清契约/数据负责人、消费与生产的契约版本、兼容与版本偏差策略、回滚/晋升负责人、绑定精确版本集的新鲜集中集成证据（另一组合的旧 E2E 不算）。
- 跨栈"完成"是分阶段的（代码落地→契约激活→流量开启→特性完成），流量开启还可能是部分/影子/分群/区域；回滚不是原子的：回退清单只恢复可部署组合，schema/MQ/已发布 app/缓存格式/外部消费者需要 expand-contract 前向兼容与明确的迁移顺序或双写窗口。
- schema/codegen 契约即代码通常只覆盖结构；默认值、时区、幂等、采样、脱敏、基数等语义一致性需要独立的语义一致性套件。
- 手工从对方实现反推出来的一致性产物是 candidate 而非权威，先由生产方运行时 harness 对真实处理器验证再打不可变版本 tag，否则消费者会钉住错误契约。
- 供应商化的镜像副本是 source@pinned-tag 的只读镜像，契约变更先改源仓再重新 vendor；合法的下游补丁必须改称 local-overlay 并带负责人/原因/到期/上游 issue 与自己的 CI；用 vendor-sync 门校验每个文件匹配源的按 tag 清单，漂移是需分类的阻塞信号而非静默合并。
- 一需求一版本边界：不把别的需求的版本折进本次集成集，但共享契约/数据迁移/开关/发布顺序/回滚路径的需求合并为联合边界；从 spec 推导的仓与版本集只是候选，要对照真实消费者对账，spec 未写的消费者算未知风险而非"不涉及"。
- 默认短寿分支 + 主干倾向：分支寿命超过 1–2 天要么拆 PR 要么用功能开关把未完功能合入主干；GitFlow/长寿发布分支只在并行维护多个生产版本、固定发布周期含稳定化窗口、热修复通道与下一版并行、合规要求隔离审计时使用；功能分支不当作功能可见性门。
- 提"加 CI 步骤/简化发布/改分支策略"至少关联一个交付指标（部署频率、变更前置时间、变更失败率、失败部署恢复时间、部署返工率）或邻近工程结果并声明权衡；指标当观察轴不当 KPI。
- 任何改代码前先建独立工作树与唯一的每线分支，绝不在主检出/main 上开发；同仓工作树共享对象、refs、hooks、config 与远端，改 hook/config/远端/gc 要协调；分支不等于并发隔离，checkout 会移动共享工作区。
- 绝不 stash 别人的未提交改动，stash 是共享可变状态；宿主安装的符号链接指向共享树时同样要隔离；跳过隔离后不要为了躲冲突而提交未评审的 WIP，先搬到独立工作树或私有草稿。
- 每线 WIP 分支保持本地私有直到共享推送与 MR 门通过，绝不 force-push 共享分支来"隔离"；合并回目标（尤其 squash）前检查是否落后并更新到目标核对冲突集，避免静默回退最近的修复；落地或放弃后清理工作树、私有分支与远端分支。

## 15. 问题排查与学习
- 铁律：不因别的路径能走就跳过问题；不删/注释/削弱失败测试来让套件通过；未经负责人明确降优先级并记录残余风险，绕过方案不算修复；根因未知时不做大范围重构。
- 七步：复现（步骤、输入、环境、日志、是否稳定复现）→隔离（缩到层/变更/依赖/条件，必要时最小复现或二分）→提出可测试的假设与证据→定点插桩（避免噪声日志）→证实或否定每个假设，错了回到假设而非猜→最小修复根因，无关清理分开→加先失败后通过的回归测试。
- 五问直到答案指向持久的预防机制（规则、守卫、流程更新）而不是那行坏代码：为何发生、为何代码/流程允许、为何测试/评审/监控没抓到、为何假设或契约不清、什么可复用的规则能防复发。
- 留证据：用户可见症状或失败命令、复现步骤、日志/trace/截图/载荷/数据状态、根因与被否定的假设、修复摘要与验证命令结果、回归测试或不可行原因、可复用教训。
- 教训落到最小的正确持久位置：流程问题进流程规则，栈实现问题进该栈参考，UI 问题进设计/前端规则；一次性业务问题不做成通用规则；只有会改变另一产品上未来行为的规则才值得写。

## 16. 既有项目评估报告
- 广谱"分析/评审这个项目"的输出是代码证据报告而非架构随笔：分开写"读过的证据"（文件、命令、配置、文档、排除的生成区）与"未验证的证据"（缺依赖、无设备、无凭据、失败命令、未跑的在线服务）。
- 没有评估启动清单（产品/用户路径、架构与实现负责人、测试层矩阵负责人、UI 面、运行时证据面、不可用/在线/手工边界、提炼触发）的工作标为 interim 探索而非完整评估。
- 发现按严重度（P1 崩溃/数据安全暴露/关键流程中断/不可逆副作用/发布阻塞；P2 可能的用户可见失败/严重可维护性风险/关键行为缺契约或测试；P3 清理与文档漂移）与置信度（verified 已复现/likely 代码强烈暗示但未执行/speculative）分开列，猜测不混进主 bug 列表。
- 不把文档主张提升为实现事实；只有构建或手工的证据不算断言式覆盖；无渲染证据不评设计质量而是声明静态评审局限。
- 每个维度写不适用原因或缺证据标记；高后果的认证/账号/权限/支付入口流程的场景矩阵必须区分自动化、手工/运行时验证、阻塞、产品缺口、仅在线、不适用，不能折叠成"E2E 通过"。
- 下一步分成快速修复、结构性工作、测试债、产品/设计、发布/运维五类并点名负责纪律；评估转修复前先出执行计划检查点（已有 spec/计划核对、计划形态决定、分支边界、选中与推迟的发现、测试登记表、任务拆分、每个修复的根因证据、失败测试先行目标、设计检查点、验证命令、停止条件）。
- 跑任何按仓的门或断言"缺某文件/配置"前先定拓扑（单仓、并列多仓的父目录、monorepo，按成员仓边界跑而非父目录）并对照已提交的 HEAD 而非工作区（先确认 HEAD 存在，再从 HEAD 读路径），记录脏工作区可能是别的会话的 WIP。
- 架构/系统概览文档签字前做诚实性检查：每条"已强制/已自动化/已经做到"的成熟度主张记录主张→证据来源→状态（implemented / convention-or-target / unknown）并对照真实代码、CI、hooks；"先进/最佳实践"只以对齐外部标准加坦诚差距的方式表述。
