# 数据看板与口径治理手册

> 从一位工程师搭建内部 BI 看板、指标语义层、定时物化与成本对账的经验中提炼，与具体公司无关；条目为通用规则，不含任何业务数值。

## 1 指标口径怎么写

- 每个指标的定义必须写清统计对象、时间归属轴、去重口径、数据源四件事，描述短于一句完整话的一律打回。
- 口径写明来源表、字段、过滤条件（状态、渠道、排除名单）与金额字段的优先级（如实付优先于应付）。
- 时间字段要指明是事件时间、支付时间还是账单自然日，并写明按哪个时区切日。
- cohort 型指标要写明归属规则：按注册日、按任务开始日还是按消费日归桶，三者互不可比。
- 身份/套餐等随时间变化的维度要写明判定时点（事件发生时、月内首次消费时、月末时），禁止用当前状态回写历史。
- 每个指标必须声明周期聚合意图（sum / distinct / snapshot），缺声明就拒绝保存，不允许静默回落为快照。
- 跨天会重复出现同一个人的用户数指标只能声明 distinct；比率、去重数、分位数不可加，必须做成求和之后的公式指标。
- 公式指标按粒度可有不同表达式（日×365、月×12），并写明它是管理口径而非财务确认口径。
- 支持粒度由引擎能力派生而非人工填写，人填意图、机器算能力，避免多一个可以说谎的字段。
- 重叠指标以已校验看板的取数规则为准，直接复用其常量与匹配条件，只加维度不改口径。
- 口径演进要保留版本标记与变更日期，废弃的草案要在文档里注明"有意废弃"而非留给后人猜。
- 指标名带口径后缀（如"·任务数""·总积分"），同一类多行若只写类别名会重名且量纲相同无从区分。
- 已知残差与近似（兜底判定、窗口外消费、估算科目）必须写进指标描述与看板说明，不在代码里拍数。
- 在"已校验"口径之外新建指标时，必须先把整条公式依赖链治干净，未校验指标不得成为已校验指标的依赖。

## 2 真相源与优先级

- 事实优先级：一手交易流水 > 系统台账 > 数据仓库同步 > 埋点平台，越靠后越只能做趋势对照。
- 收入口径以支付平台成功流水为准，退款、渠道手续费是否冲减要显式声明并全局一致。
- 成本以供应商刊例价×用量反算为直接成本，账单总额只能给月度校准因子，不能替代身份维度的拆分。
- 事实层只记"发生了什么、刊例价多少"，归因层只做"按口径摊给谁"，口径变了只改归因层并回算。
- 埋点是否仍在用只认平台上的"最近上报时间"，代码里存在不等于线上有数据。
- 建立埋点真相源表格：业务指标→事件名→发起/完成环节→工程→代码位置→最近上报→状态（生效/低频/废弃/有码无数）。
- 多源同名事件（多个服务都上报）要标出主源，老源退出时记录断点日期，跨断点不可直接接续趋势。
- 事件从前端迁到服务端产出时要逐属性对照：同名不同值域、属性消失、值域整体替换都会让老看板静默归零。
- 可缺失的属性要在写入侧省略而非发 0，读取侧显式处理缺失，且绝不用它做分子过滤。
- 平台自建看板与内部语义层是两套口径，允许并存但必须标注，不得在同一张表里混用。
- 定期用平台 API 反查所有看板引用的事件，列出"已废弃仍被引用"清单，活跃看板逐报表替换，零浏览看板整块归档。
- 定时抽取会过期的原始事实（如短保留期的运行时事件）到自有表，只存事实不存分类结论，口径定了再算。
- 抽取表要字段白名单化并用测试锁死，任何 `is_xxx` 式结论字段出现即测试变红。
- 死快照集合（一次性写入、无定时刷新）不能做筛选真相源，先查刷新机制再决定能否用。

## 3 校验方法

- 每张看板先写结构恒等式：分项之和恒等于总量、占比之和恒为 1、子集不大于全集，并用测试锁死。
- 恒等式要建在未取整的日序列上，引用已按展示精度取整的公式会在完全正常的数据上报出假差额。
- 区分"闭合核对（差额应恒为 0）"与"口径差（本就不为 0）"，后者单独成组并在说明里写清为什么不为 0。
- 子集不变量证明力有限：它排除负值与越界，不证明总量正确，报告里要如实标注。
- 跨看板对账要解释每一分差额来自哪个口径差异，"逐分相等"若隐含某类数据为零，这个前提要向业务确认。
- 与手工表对账时逐日拆开看，能区分"口径分歧"与"手工漏填"，不要只看合计差异率。
- 常识边界检查：人均、比率、单价落在合理区间，某月付费用户数骤降到个位数就是聚合策略错了。
- 抽查原始记录：对账口径前先去线上数一遍字段是否在顶层、是否嵌套、覆盖率多少，不凭记忆写字段路径。
- 用比值消除流量波动，人均次数≈1 通常意味着只剩一条路径在触发，比值翻转日才是口径断点。
- 按事件属性拆分定位坏掉的路径，某个来源归零是链路挂了而不是用户行为变了。
- 校验身份归因：统计 user_id 为空的比例，排除"事件在发但身份丢了"。
- "已校验"标签按指标打而不只按看板打，入池判据写成不变量测试，新增看板自动受护栏保护。
- 已知数据链路有问题（采集断、估算科目）时整板不打已校验标签，修好再入池。
- 变异测试是入池护栏的一部分：删声明、改依赖、塞不支持粒度的指标进看板，测试必须变红。
- 首次上线不授予已校验，自动化不变量、真实数据只读探针、业务人工核对三者齐全后再单独授予。

## 4 时区与时间窗

- 看板统一时区写在一个模块里，所有 SQL 用显式 UTC 边界替换数据库的 `CURDATE()`，避免会话时区漂移。
- 支持多时区切换时按 UTC 小时桶存储，本地天由时区库实算所覆盖的 UTC 小时集合，不假设一天 24 小时。
- 非整点偏移时区在读路径 fail closed 报错，不给近似值。
- 时区必须进入缓存键，否则切换时区会读到另一时区的旧结果。
- 数据仓库对埋点平台的同步是 T+1，最近一两天的"暴跌"先用平台导出接口复核再下结论。
- 埋点平台按项目时区切天，复算本地天要再按 UTC 小时窗口过滤，否则错位若干小时。
- 账单等自然日数据要先定它属于哪个日历，再摊到 UTC 小时桶，月合计才能与账单精确相等。
- 事件日与 cohort 日不同：按注册日归桶每人只落一天可 sum，按活跃日归桶同一人落多天必须 distinct。
- 前向留存的最近若干列必然为空，只在下一周期完整结算后才计算，不要把未结算周期显示成 0。
- 当前日/当前月标"截至当前"，读者不会把只算到今天的数拿去做环比。
- 月度指标按月度汇总后的分子分母重算，禁止对日比率取平均。
- 双币展示时月本币金额等于逐日换算之和，不能用月末单一汇率乘月合计。
- 定时任务的时间参数一律按 UTC 解释，容器本地时区不可依赖。

## 5 取数与性能

- 不抽样，聚合尽量下推到数据库端，客户端只收分组结果。
- 大用户集合禁止物化成 `IN` 列表传给查询，改为把判定条件下推进 SQL，或取当日有界候选集再求交。
- 缓存必须可证明生效：缓存键包含时区、筛选摘要、常量指纹，改常量后看板立刻变化才算生效。
- 一次多指标请求内共用一次批量读取，请求级 memo 存 Task 而非结果，避免并发穿透；memo 键两处各写字面量等于静默读两次。
- 游标批量大小显式钉住，往返次数与行数解耦；开发机经隧道的耗时不能当生产性能结论。
- 行数上限用"请求 limit+1，超限即抛错"，禁止静默截断后把不完整合计当已核对事实。
- 客户端加并发救不了服务端瓶颈，实测并发翻倍总耗时几乎不降就该转向预计算。
- 定时物化框架的契约：只有可加数值序列能物化，计算窗口与存储桶分为两个参数，计算窗口必须是桶的整数倍。
- 桶值必须与计算窗口无关，一份桶能卷成多个时区的天，两条性质各自写测试守住。
- 物化桶存未取整原值与非派生值（如只存美元不存本币），取整、汇率等在读路径一次完成。
- 多 measure 的桶只写非零字段并整篇替换，稀疏存储把文档体积降一个数量级。
- 物化的 compute 会被看板实时补算在 HTTP 请求里调用，全表扫、算权重、写库、种常量一律放 prepare，compute 严格只读。
- 首次运行只做最近一个窗口，历史交给显式 backfill；单次上限必须大于尾部重算窗口，否则积压时活锁而日志全绿。
- 水位线只推进到连续成功的最长前缀，compute 返回的桶数必须恰好覆盖被要求区间，多一个少一个都报错。
- 每个物化任务一个定时任务、失败即非零退出、设活动超时，不做"一次跑全部任务"以免连坐。

## 6 失败可见

- 查询失败显示"失败"并可单指标重试，绝不静默补 0；补出来的 0 与真实低谷在界面上无法区分。
- 查询失败与查询成功且确实为零要分开：前者为空并带错误原因，后者才显示 0。
- 依赖指标失败时公式、双币伴随值一并继承失败状态，任何单一来源失败不得生成部分比率。
- 分母为零但查询成功时显示"-"而非 0%。
- 常量缺失时抛错而非回落 1.0 或 0，"常量没配"表现成"成本骤降"是最糟的失败模式。
- 校准因子缺失、账单未采到时该月留空不兜底成 1，兜底会把刊例价伪装成结算成本。
- 物化水位线之前缺桶报错，之后走实时补算并设尾巴上限，没有物化路径的看板直接失败不降级。
- 口径版本标记写进每个桶，一天每个小时桶都带标记才出数，未重算的历史显示"-"而不是 0。
- 上游依赖未就绪（抽取未覆盖）与"那天真的没数据"要能区分，用实际抽取覆盖判定而不是水位线上界。
- 组合行里有一个来源失败就整行标失败，不能把失败当 0 加进合计。
- 定时任务吞异常返回 0 会让连续失败显示为一切正常，症状只剩"看板不更新"。
- 审计写入失败不改变业务任务成败，但绝不能用记账失败掩盖真实的物化失败。

## 7 重算与清理

- 回填前先判断目标集合属于哪种存储语义：整篇替换、累积合并、写定不覆盖，三者重跑效果完全不同。
- 整篇替换（ReplaceOne）重跑会清旧字段；`$set` 只覆盖写出的字段，废弃 measure 的旧值会永远留在库里。
- 累积合并（`$addToSet`/`$min`/`$max`）幂等但只增不减，抽取口径改了必须先 drop 受影响文档再全量回填。
- 写定不覆盖（历史月份、已确定汇率）正常重跑改不动，修错值走显式 `--force`。
- 回填后要核对废弃字段读出来是 0 而不是残留旧值；废弃指标名也要进删除清单并在启动 seed 时清理。
- 回填区间必须连续，首跑水位线之前、回填终点之后的桶会永久缺失。
- 尾部重算窗口吸收迟到数据（补录、退款、状态变更），更久远的变更靠显式回填。
- 物化把"查询时计算"变成"计算时计算"：改定价、改内部名单、改汇率不会自动追溯历史，要写进看板说明。
- 汇率按桶所属月份取，不按回填窗口起点取一次，否则同一个桶的金额随窗口切法而变。
- 分摊/定价在会话分摊之前按定价组完成，按会话拆开定价会让总额随分组方式变。
- 数组类累积字段设上限，截断时必须先标记再截断、并用带旧值条件的 CAS 写入，并发下不会覆盖。
- 记录每一次改写历史的回填（任务、区间、窗口数、状态、触发人、原因），空转不记；口径调整、常量变更、回填合成一条时间线。
- 首次运行只物化最近一天且水位线只增不减，部署后必须显式回填历史。
- "已结算"只能由对账行说了算，月份过去不等于账对上。

## 8 假数据与测试脚手架

- 假集合模拟聚合必须按管道里写的取值路径执行 `$group`/`$project`，不能按业务字段名直接读顶层。
- 夹具文档形状必须与线上一致，不确定就去生产按顶层字段 `$exists` 数一遍。
- 修完假集合后对假集合本身做变异走查：改回硬编码顶层，测试必须变红。
- 不要 stub 你要验证的核心交互，多步链路至少一条真实集成测试断言可观测结果。
- 两侧单测各自 mock 掉对方时接口形状错配发现不了，加一条"compute 输出不经变形直接写入存储"的测试钉死。
- 用逐日不同的数据写断言，收入恒定时"合计口径比率"与"日比率平均"数学上相等，那种数据写的断言是假绿。
- 断言"单调递增"不够，原地不动也满足单调，要断言严格单调且无重复。
- 测试用例要有反证：回看窗口配置改了必须触发重分类，不改则必须不触发。
- 变异验证先提交再改，用模式而非行号定位，format 后行号漂移会把 sed 打空成假绿。
- 只读探针必须真的只读：进程内禁用缓存客户端，不写库不写缓存。
- 前端逻辑抽成纯函数放源码目录、测试放测试目录，判断有无测试要搜整个前端目录与 package.json。
- 镜像构建若不读锁文件，传递依赖发新版会直接进生产，部署失败先看是不是依赖漂移。

## 9 与产品/运营的口径对齐与交付

- 需求文档不等于方案文档，未评审的口径不开工，口径确认记录要落到需求项评论区。
- 问 PM 问题要编号并附建议默认值，含糊回复不算答完，逐条追问。
- 每个口径决定要有拍板人与日期，并写进设计文档的"已确认口径"表。
- PM 要数据时先查看板有没有：有的说明在哪看、怎么切换、有什么局限；没有的跑只读脚本出表进文档并开查看权限。
- 交付评论里给链接、内联关键数字、看板入口、身份判定逻辑、现有表的局限、后续顺序，不写交付时间承诺。
- 管理口径与财务口径的差异（MRR 含一次性收入、年付全额计入扣款月）必须在看板说明与指标详情同时展示。
- 一个数值说明要同时出现在类型目录描述、单条指标描述、设计文档三处并由测试绑定，Agent 常常只读到其中一处。
- 看板不打已校验标签本身是产品信号，用户一眼可辨哪些数能拿去汇报。
- 展示层不隐藏口径现状（某行长期为 0 是数据事实），要保留未知/未标记行避免新工具上线后漏统计。
- 两个目标不合并成完成率，一个目标的富余会掩盖另一个的缺口，并排给差距。
- 固定业务目标放代码常量随发布可追溯，按天生效的费率放常量层；两者不混用。
- 改历史常量等于篡改已核对的账，只允许新增生效记录或删除写错的那条。

## 10 常见错误清单（现象→根因→防御）

- 筛选后数值反而变大→过滤施加在排除集而非被计数人群→过滤只作用于 behavior，并核对 ad + non_ad ≈ all。
- 未选筛选时数值也变了→筛选分支影响了默认路径→铁律：默认选项下查询规则一行不动，用改动前后一致性测试锁死。
- 昨天总是偏低、T+2 恢复→混合源今天/昨天与历史走不同身份字段→按字段别名回退并分口径各算一遍对比。
- 月视图付费用户数掉到个位数→跨天 distinct 被声明成 sum/snapshot→跨天用户指标只能 distinct，写入时校验拒绝。
- 看板数字与账单差固定比例→单价按一个汇率折美元、对账按另一个折回→刊例价存原币种，同一结算汇率往返。
- LLM 成本高出数倍→prompt tokens 已含缓存命中又被加了一次→按供应商家族定义有效输入 tokens 并收进共享函数。
- 三个月区间全部超时→每个歧义对一个子句，子句数随窗口线性增长→预计算到小时桶，实时只读桶。
- 改了常量看板没反应→常量指纹不在缓存键→缓存键拼常量的最大更新时间。
- 物化日成本与实时路径差一分→分组各自取整再求和、浮点噪声压在半分边界→读边界一次取整并先量化到 1e-6。
- 任务每小时都跑但水位线不动→单次上限不大于尾部窗口→构造时校验并报错。
- 某月完全没有消耗的假象→新增 measure 在历史桶里根本不存在读出为 0→口径版本标记，未重算显示"-"。
- 抽取静默停摆→数组逐天增长顶破文档上限写入失败→批次与落库两处截断都留痕。
- 假集合一直绿、线上口径错半年→夹具按顶层取值、管道写了错路径→假集合照管道执行并变异走查。
- 部署失败怀疑本轮改动→镜像现场解析依赖、传递依赖发新版→比对发行版本用 importlib.metadata，钉住版本。
- 后台服务几分钟后无故消失→进程组被清理→以新会话方式脱离启动。

## 11 看板评审清单

- 每个指标是否写清对象、时间轴、去重、数据源，并声明周期聚合意图？
- 所选粒度是否都在指标支持粒度内，公式依赖是否全部已校验？
- 时区是否显式、是否进缓存键、当前周期是否标"截至当前"？
- 恒等式、闭合核对行是否存在且建在未取整序列上？
- 失败是否显示失败、依赖失败是否传播、分母为零是否显示"-"？
- 默认筛选下与改动前是否逐值一致？
- 大集合是否下推而非 `IN` 列表，一次请求是否只读一次基础数据？
- 物化任务的 compute 是否只读，prepare 是否承担全部重活，单次上限是否大于尾部窗口？
- 目标集合的存储语义是否判定，回填是否清理旧值，回填区间是否连续？
- 假集合是否照管道执行，是否有真实链路集成测试与变异走查？
- 已知残差、近似、未接的数据源是否写进指标描述与看板说明？
- 是否记录了口径版本、拍板人、变更时间线，已校验标签是否在探针与人工核对后单独授予？
- 前端取主表是否按 id 而非索引/类型，新增 widget 是否带与主表相同的控件配置？
- 替代口径速查表是否随废弃事件一起给出，活跃看板的过时引用是否有替换计划？
