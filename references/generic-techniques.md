# 通用工作技法（与任何公司/产品无关，可迁移）

每条按"什么时候 → 做什么 → 怎么验证"写。共 57 条，已合并重复项。证据归档在 skills-archive。

## A. 判断与取证
1. **常识先于数据。** 拿到任何数字先过业务常识（分母不能小于分子、长周期不能小于短周期、有新增就该有活跃）；不通就重查，不接受"看起来是"。
2. **恒等式对账。** 拆分指标要有一条能加回总数的等式，总数再从独立路径算一次做对照。
3. **真相源分层。** 现状看运行环境实际配置 > 代码 > 文档；意图看已评审的需求文档；口径看已校准的基准。文档写错先改文档，不绕过。
4. **复现是决策前提。** 不能复现就不下结论；造最小复现账号/数据，跑真实链路后拿 ID 查落库记录。
5. **边界值追问。** 规则定下来后立刻问 0、1、临界值、并发双开、取消/失败/超时。
6. **规模意识。** 本地小数据能跑不等于线上能跑；先估线上量级和耗时，再定分段、分时、只读快照。
7. **双向校验。** 用现状核对问题清单是否真实存在，再用问题清单反查现状描述是否正确。
8. **假设自己提、事实来证伪。** 先给根因假设，让执行者用日志/数据推翻或确认；结论前后不一致时逼回单一结论并要证据。
9. **精确不估算、按 ID 不按金额。** 时长精确取，对账按 ID 匹配，用量字段原样打印确认来源。

## B. 方案与范围
10. **先方案后代码。** 非一行修复都先出方案，让 AI 复述确认，评审后再动手；方案落到团队正式文档面。
11. **方案收敛。** 只保留当前方案；删废弃选项、过程痕迹、"更正后"字样；总分总；每个能力标注属于哪次交付；写"当前影响"和"上线后效果评估"。
12. **对方案做对抗式追问。** "还有什么没考虑到""攻击者怎么绕""有没有成熟三方可接入""还有哪些异常场景"，直到堵住绕过路径。
13. **改动收敛。** 不影响原有逻辑、不改无关模块、能复用不新造、职责放在正确的层。
14. **根因优先于兜底。** 事件驱动是主路径，定时任务只做兜底；不用 fallback 掩盖问题；一致性不能用"重试 3 次"代替。
15. **扩展性不够就重做，但不刷历史数据。**
16. **先问收益和成本再决定做不做。** "做好之后有什么好处""现在立马能做且有效的是哪些"；成本高的先待定。
17. **分级止血。** 资损类短期快速拦，资产防护类给迭代周期；先 P0；坏了先回滚或关开关再查根因。
18. **工作量按 AI 辅助开发口径估，但要诚实。** 不虚高也不假装能省 90%；考虑跨模块依赖。

## C. 交付闭环
19. **固定流水线。** 新分支 → 本地 lint/test/e2e → 按仓库规则自审 → 描述与 diff 一致的 MR → 人合并 → 评审意见逐条回修 → 真实环境验证 → 配置逐环境核对 → 部署顺序 runbook → 状态流转 + 评论 → 上线看效果 → 复盘回写规则。
20. **评审结论看正式渠道。** 以评审系统最新一条为准，不以流水线是否绿为准；同类意见被点名两次就前置成规则/检查。
21. **一个目标分支只留一个 MR。** 子任务先合到功能分支再整体合入。
22. **验证分工。** 人负责配置、启动、真实身份走链路；AI 负责监控日志、查库、比对。
23. **验证过程写进交付物。** 对接文档带验证步骤与结果；手工回归写进 issue；校验通过的看板打标签。
24. **配置变更三问。** 新增了哪些配置项、各环境配了没、默认值是什么；提前备好的配置只写入不重启。
25. **灰度节奏。** shadow → observe → enforce；有证据时直接 enforce；开关不为加而加。
26. **上线后回看。** 几天后对比指标；预期该升的没升当 bug 查；复盘结论改进规则/脚本。
27. **先测一条再批量。** 批处理脚本先跑 1 条、再 100 条；备好可重复的清理脚本。
28. **收尾三件事。** 删调试日志、删废弃代码/配置、运维说明随交付（配置清单、脚本用法写在脚本头）。
29. **阶段复盘。** "总结今天完成的功能""复盘从开始到现在的关键节点"，输出同步任务系统。

## D. 生产与风险
30. **写操作分权。** 只读先行、先备份、先评估影响面，再逐项授权；执行后回读确认。
31. **不动别人的环境。** 共享测试环境、别人的本地服务、别人的 .env 都不碰；热更新不重启。
32. **凭据不进对话。** 只给变量名和存放位置。
33. **有 CLI/API 就不用浏览器。** 让 AI 操作 GUI 成本高且易错；没有 CLI 先做一个。

## E. 协作与沟通
34. **正式文档面唯一。** 方案、结论、验证结果都同步到团队正式文档；原地改、不新建、不覆盖他人评论。
35. **问题编号、附默认值、追问。** 问产品/同事时 1、2、3 编号，每条附建议默认值；没答的追问。
36. **对象带名称。** 工作项、MR、分支、任务出现时都带名称，不只给 ID。
37. **结论先行、一句话可转发。** 先结论再依据；文档不写排查过程；去缩写、去黑话；看不懂就打回。
38. **发版说明带作者，任务拆子项防丢目标。** 父子关联、负责人字段。
39. **建机制而不是单点解决。** 同一件事第二次出现就沉淀成 skill/脚本/真相源表格/团队规范。

## F. 驾驭 AI 助手
40. **交接稿格式。** 新会话/换工具时用"任务 / 已完成 / 关键事实（不可回退）/ 结论 / 下一步"开题。
41. **发散或连续失败就换策略。** 方案越聊越散、或"还是不行"第 3 次时停下：回滚、缩范围到一个文件或只改 prompt、贴可工作的对照代码或官方示例、换会话让它"总结已确定方案再对齐代码"。
42. **长时间无人值守要给边界。** 交代可参考的规范、要做的测试、不要问的事项、回来要看的产物，然后放手。
43. **进度可见性。** 长任务要求主动汇报或自行轮询；不接受"停下来等确认"；子任务并行的前提是能看到进度。
44. **规则前置，不口头重复。** 同一纠正第二遍就写进规则文件/skill/memory。三个已验证的时机：团队引入新人时写开发规范；任务系统踩坑后写约束文档；评审反复不过时把规则文件从"参考信息"改成"架构红线"。
45. **让 AI 给选项，自己单字选。** 业务规则自己拍板到字段级；技术细节授权 AI 定。
46. **评审意见回灌闭环。** 把评审机器人/同事意见原文贴回，让 AI 逐条修并复核，再由人合并。
47. **确认 AI 在正确环境跑。** 进你的 venv/包管理器、连配置里的 host 而不是 127.0.0.1、用你已开的端口。
48. **按官方文档/示例压 AI。** AI 瞎写时贴官方 quickstart 逼它对齐；升级依赖先查官方版本矩阵。

## G. 后端 / Agent 设计原则
49. **默认分布式。** 定时任务、锁、回调一律按多实例设计（"A 拿到锁挂了 B 怎么办"）。
50. **失败透传上游重试，事件按 ID 去重。** webhook 本地失败要返回错误让平台重试；N 条事件不能变 N 条流水；同一用户在支付平台最多一个订阅。
51. **协议字段显式化。** 流式加类型字段和结束标记，不靠文本标签；消息有 id；报警带执行者和最后错误；"作废"用独立方法。
52. **鉴权全环境一致。** 回调可豁免中间件但不能无认证；所有环境都加；先跨域再鉴权。
53. **让模型做语义判断，代码只做规范化。** 判断类逻辑不硬编码；主 agent 生成、工具只规范化输出；确认门禁类问题层次在 prompt 不在代码。
54. **对冗余调用零容忍。** 页面一加载调三次接口不行；能在后端做的不走前端。
55. **并发是默认。** 循环阻塞就并行；并行数可配置；异步里嵌同步要查。

## H. 学习与上手
56. **用真实任务熟悉系统，不先问架构。** 第一天就改业务代码，顺着报错和数据流问局部问题；环境坑丢给 AI 当"翻译器"。
57. **陌生框架先私下建 demo 再回项目。** 从官方 quickstart 起步。
