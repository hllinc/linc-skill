# 可观测性手册（展开）

展开 SKILL.md §1.1 与 §5.7：排查时怎么从遥测回溯，发布时怎么证明改动可观测。A 部分是最低要求，B 部分按主题展开。

# 可观测性手册

## A. 排查与发布时的可观测最低要求（≤12 条）

1. 每条结构化日志必带：时间戳（含时区）、级别、消息、log-id、trace-id、span-id、trace-flags、服务名、环境/lane、区域、集群、pod、调用位置；ERROR 及以上另带 `_stack`。
2. log-id 在边缘生成（缺失或格式非法时重生成），经 HTTP 头、RPC 元数据、消息队列属性原样透传到每一跳，并回写到响应头供用户报障。
3. trace 上下文按 W3C `traceparent`/`tracestate` 跨服务透传；日志库必须从 ctx 自动取 trace 字段，允许不带 ctx 打日志即视为框架缺陷。
4. 外部入口不信任入站的 lane/路由/trace 头：lane 由网关从已认证身份推导，外部 `traceparent` 只做 link 不做 parent。
5. 上线后必看四个信号：QPS、延迟直方图、错误率、饱和度；再用一个真实请求做闭环：响应头拿 log-id → 日志检索命中全部跳 → 点 trace-id 看到多 span → 看板 QPS 有抬升。
6. 告警阈值基于 SLO 燃烧率而非内部计数：30 天预算下 P0 = 1h/5m 窗口 14.4× 或 6h/30m 窗口 6×，P2 工单 = 3d/6h 窗口 1×，长短窗同时超阈才触发。
7. 每条告警必须带 runbook 链接；无 runbook 不允许定 P0；P0 只走值班人必看的实时渠道加升级，禁止只发邮件。
8. "线上是否启用"以生产实际生效状态为准：查运行中的配置、开关求值结果、真实请求产生的日志/指标证据，不以代码里有分支或已合并为依据。
9. 接线不等于生效：驱动一个真实请求穿过真实 HTTP/RPC 服务，断言 handler ctx 有 trace-id/log-id 且业务与访问日志都含这些字段，才算关联生效。
10. 日志中禁止出现：token、密码、身份证/手机号等完整 PII、授权码、PKCE、Cookie、原始请求/响应头与体、签名 URL、原始 prompt/转写文本、账号邮箱与稳定用户标识；敏感头默认掩码。
11. 指标标签禁止用户 id、租户 id、请求/日志/trace id、原始 URL、自由文本、时间戳；实例标识（pod/ip）不作默认标签；新增标签先算基数，预估超 1e6 序列即拒绝改用 exemplar。
12. 无法计算的信号显式登记为盲区（"不能测 X 因为 Y"），不得假装有覆盖；上线证据缺任一项即视为未完成。

## B. 展开手册

### B1. 日志 schema
- 平台保留字段以 `_` 前缀命名；应用字段一律用 `app_*`/`biz_*` 前缀，禁止自造 `_` 字段。
- 级别取值固定为 TRACE/DEBUG/INFO/WARN/ERROR/FATAL；时间戳同时提供 ISO-8601 与 Unix 毫秒并记录所用时区。
- 采集层禁止允许应用覆盖保留字段；至少一层防护：管道剥离并从编排元数据回注 lane/服务/集群/pod，或 SDK 为唯一写入口并加 lint。
- 每个字段值先脱敏再截断，在 UTF-8 码点边界截断并记录截断标记与原始长度；禁止截断整条 JSON。
- 在入口处限制字段数、嵌套深度、单字段与整条事件大小；超限时先丢非必需字段，保留全部保留字段。
- 审计、账本、事故关键内容不得采样或截断，走独立的持久化非采样路径。
- 日志库必须对重复行限速（按服务、错误类、路由模板、环境、级别分桶），暴露丢弃计数，首现、状态变化、审计事件不得被采样掉。
- 框架中间件禁止逐请求打 start/end Info 日志。
- 保留策略按类别分开：审计长期、业务约 7 天、调试 1–3 天；生产与非生产日志后端分离。
- 既有服务改字段名必须别名或双写并迁完消费者再下线旧名，禁止原地重命名。
- 文件落盘与 stdout 二选一，全平台统一，不混用。

### B2. 日志与 trace 关联
- 三个 id 各司其职：log-id 给人报障、trace-id 跨服务连接、span-id 标识单段工作；三者必须穿过 HTTP、RPC、队列每一种传输。
- 队列无头支持时用 JSON 信封携带 `_log_id`/`_traceparent`/`_tracestate`；吞掉关联 id 的服务不允许上线。
- 全栈只定义一次复合传播器；extract 兼容 W3C 与 b3，inject 只发 W3C；组合列表末位优先，要让 W3C 胜出需把 TraceContext 放最后并用冲突测试固化。
- b3 采样位要映射到 trace-flags；b3 缺省采样状态视为"延后"，本地重新决策，不得压成 00。
- 先全量部署兼容抽取，再切 W3C-only 出口，顺序不能反。
- 头/元数据按各自传输规则规范化大小写；重复或冲突的传播键拒绝而非后者覆盖。
- 关联字段在记录工厂或 handler 层注入，禁止挂在祖先 logger 的 filter 上（子 logger 传播时不会执行）。
- 异步脱离请求生命周期的工作只白名单携带关联字段与工作项标识，禁止整体复制请求上下文（会带走鉴权与秘密）。
- 日志工具与 trace 工具必须互相可一键跳转；span 属性镜像 log_id。
- 每次框架大改后跑端到端冒烟：无 log-id 请求 → 响应有生成值 → 日志按 log-id 命中所有跳 → trace 多 span → span 服务名与日志服务名一致。

### B3. 指标命名约定
- 基线标签由框架客户端自动附加：服务、环境/lane、区域、集群；业务代码只传领域标签。
- 允许的领域标签：模板化路径、handler 名、方法、错误类枚举、状态码类；跨表面的错误分类编码为一张共享枚举表，禁止各处手写 `if code == X`。
- 命名格式 `<domain>_<noun>_<unit>_<aggregation_hint>`，全小写，单位用基础单位（秒、字节），禁止泛名与业务域泄露。
- 单调累计用 Counter；队列深度、连接数等双向值用 UpDownCounter；饱和度用异步 Gauge；延迟用 Histogram。
- 直方图桶边界由平台声明且必须包含 SLO 阈值；SDK 默认桶需评审后才可用。
- 服务级看板从 Golden Signals/RED 起步，资源级从 USE 起步，可混用，但不替代 SLI/SLO 设计。
- 每平台只选一种指标出口（抓取或推送），一个进程一个指标只走一种；迁移期双写需隔离管道与去重方案。
- 长期存储与抓取层分离，看板与 SLI 查长期存储。
- 观测代码不得侵入被观测路径：不加重试、阻塞或业务分支；但审计、计费类记录是业务写，不适用尽力而为。
- 新增事件、指标、面板前先盘点已有信号并复用，避免近似重复分裂历史。
- 跨层结论（客户端 ↔ 后端）必须用对齐的标识或时间窗，两侧各自计数相同不算证据。
- 开启 GenAI 语义约定前先审计该 instrumentation 是否默认采集 prompt 内容；内容只走 trace 事件，禁止进指标标签。

### B4. SLI/SLO
- SLI 从用户可见旅程定义，不从内部计数器；"DB 可用"是探针不是 SLI。
- 每条旅程至少一条可用性 SLI（成功/有效请求）和一条延迟 SLI（延迟 ≤ T 的占比，分母为有效集）；P95/P99 只是看板辅助。
- 队列型流程增加新鲜度 SLI 与吞吐 SLI。
- SLI 必须能写成对长期指标存储的具体查询；写不出即指标不全，先补指标再宣称 SLI。
- 延迟阈值 T 必须是真实存在的直方图桶边界，否则先迁桶。
- 目标值参考：新服务 99.0%、成熟服务 99.9%、支付/登录关键路径 99.95%；无 7×24 值班不得起步 99.99%；100% 等于没有发布预算。
- 错误预算 = 1 − SLO，默认滚动 30 天；预算耗尽即停止非关键变更直到恢复。
- 燃烧率告警按多窗口分层，每层长短窗同时超阈才触发；1 分钟窗口的燃烧率会误报，禁止。
- 燃烧率规则的两个窗口必须聚合到相同的告警身份标签集，窗口放在指标名不放标签，否则交集为空永不触发或跨区误报。
- 发布晋级必须先查 SLI 与预算：灰度期间燃烧率在预算内且窗口累计预算未耗尽才可晋级。

### B5. 告警与值班
- 用户症状用 SLO 燃烧率告警；容量与临近故障可用白盒指标，但要记录预期故障、阈值依据、动作与负责人；纯诊断信号只进看板不告警。
- 严重度与渠道固定：P0 值班群加电话推送，5 分钟内响应，10 分钟未响应升级次值班；P1 团队频道工作时间内 1 小时响应；P2 每日摘要；寻呼只用于 P0。
- 每条告警必须带 runbook 链接，投递适配器直接丢弃无 runbook 的告警以倒逼作者补写。
- runbook 一屏以内：摘要、首查一条查询、常见修复一条命令、升级对象、复盘模板链接；更深内容用链接。
- 新增或修改告警规则时列出应喂该指标的全部埋点并逐个核实已埋，清单随告警一起提交。
- 新告警按故障、健康、恢复三种场景验证后才生效。
- 告警评估与投递二选一模式（AlertManager 或看板直连 webhook），每环境只用一种；webhook 接收端必须有重试。
- 值班交接必须发布：收到页数、已解决与升级数、未结事故、应解除的静默。
- 反模式：P0 只发邮件、无 runbook 的告警、对每个原因告警、把静默当长期修复。

### B6. 框架中间件清单
- 四个必装中间件按序：ctx_inject → tracing → metrics → recovery，随后才是 CORS 与业务 handler；顺序不可调换。
- 只允许通过统一的 `NewServer()`/`NewClient()` 构造服务；业务代码禁止手动重复挂载同名中间件，防止指标双计。
- ctx_inject 负责读取或生成 log-id、确认 span 在 ctx、注入 lane 与服务身份、把 log-id 回写响应头。
- tracing 记录方法、模板化路由、状态码，5xx 标 error；子 span 必须从上一个返回的子 ctx 启动，否则变成多根或兄弟。
- 队列消费 span 默认对每条消息的创建上下文加 link，仅单消息 Process span 可额外设 parent；只有 IsRecording 为真的 span 才会保留 link。
- metrics 记录请求总数、延迟直方图、5xx 错误计数（带错误类标签）。
- recovery 捕获 panic：ERROR 日志带栈、panic 计数器加一、返回固定 500 错误码、进程不退出。
- 健康检查 `/ping`、`/healthz`、`/readyz` 由框架自动注册；本地开发同一套中间件必须可用，禁止只在生产发信号。
- 安装期多钩子注册要全有或全无，失败回滚只清理自己的钩子；重复安装不得累积重复钩子。
- 可选遥测自身配置缺失时构造 pass-through 而非 panic，但要发出可见的降级诊断，且 ctx 注入、伪造头剥离、panic 恢复等强制职责仍必须执行；审计、鉴权、计费类钩子不适用 fail-open，必须 fail-closed 或先持久化再继续。
- 请求级传播状态存在并发域本地存储（ctx/contextvars），每个终止路径都重置；流式响应用 exactly-once 终结器结束 span 并区分客户端断连与服务端超时。
- 每个适配器必须有"未接线构造"测试：nil 运行时下一个请求不 panic、按分类得到透传或拒绝结果。
