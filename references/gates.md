# 硬性门禁总表（按阶段）

每个阶段"不满足不能继续"的条件。展开做法见各手册；本表用于 SKILL.md §10 自检前逐条核对。

## 1. 产品研发工作流（顶层生命周期）
1. 第一行实现编辑前必须存在活动基线（当前分支未合并的 spec/计划）与实现边界记录；「继续」不是豁免。
2. 行为变更必须测试用例先行并 RED 后再编码；每个代码改动至少一个相关测试层在本轮跑绿。
3. 推共享分支/开 MR 前风险所需测试层在最终状态上绿；diff 自身的红构建永远阻塞；合并需用户对该 MR 的明确指示。
4. 触发技术设计闸的工作必须有持久化的自评行 + 独立对抗评审记录（绑定实际 diff），仅 spec+计划到实现是流程缺陷。
5. 可见 UI 改动第一行编辑前完成设计面分类与 Phase 0，否则显式记录 visible surface: no。
6. 无本轮新鲜验证证据不得声称完成；只能用 complete / pre-runtime-test-ready / blocked 收尾；交付文档外发前必须过文案收紧与保密检查。

## 2. 需求意图澄清
1. 产品意图、目标用户、成功标准三者均有记录，或明确列为人类决策待关闭项。
2. 每个功能点至少一个可观察 pass/fail 验收条件。
3. 已知/未知分离，每条已知有来源，每条未知有 accountable owner；用户路径含异常/取消/回退。
4. 关闭表无任何整行被设为 closed；自动填写项均能指出已批准 policy。
5. 安全 4 问：记「无命中」，或四项逐条作答 + 写明依据文件名；读取不可得时写「不可得(原因)」并标 interim。
6. 证据不足的结论不得写成事实；本技能不判 PRD Ready。

## 3. 需求现状盘点（as-is）
1. 每条现状结论有具名来源 + freshness + 可信度；已查与未查类别（及原因）都写出。
2. 不下产品决策；没有任何结论由活跃度、可运行性或「另一候选已停更」单独推出。
3. 候选组件必记自述定位或「未查到 + 已查来源」；层级归属现状/目标两栏分填，不得推断。
4. 三态判定已记录；判 not-applicable 时每条前置条件逐条写明依据。
5. 未查到不得写成不存在；关闭表只填证据推导字段，无整行 closed。
6. 安全 4 问逐项作答 + 依据文件名，或显式「无命中」；不可得时标 interim。

## 4. 需求范围界定（变更边界）
1. in/out 每一项都是可审查的行为边界，无模糊标签。
2. 受影响对象十类逐类过完，不适用显式写「无」。
3. 每个切片都有可观察验收边界和不验收项；安全命中的负向用例已在验收范围内。
4. P0 核心 in/out 标人类决策，未被 agent 自行关闭；as-is 证据未被用来裁决范围。
5. appetite 已判适用性：适用子项有决定或明确未决状态，不适用有依据；未知项不抹掉也不阻断其余材料。
6. 关闭表任一适用子项 open 时复合字段与整行保持 open/blocked；安全 4 问逐项作答 + 依据文件名或显式「无命中」。

## 5. 缺陷诊断
1. 未亲眼读到失败方自身证据（断言 diff、堆栈、trace/日志切片）前，任何根因只能标为假设，不得据此修复或写入 commit/MR/报告。
2. 缺陷未先跑过该层的有界常规补救，不得记为不可复现/环境不可用/阻塞。
3. 修复必须配一条先红后绿的回归测试（或记录不可行原因与最强替代检查）；禁止删除、注释、弱化失败测试来让套件通过。
4. 未跑并读过新鲜验证结果，不得声称已修复；变通方案不得称为修复，除非负责人明确接受权衡并记录残余风险。
5. 原因未知时不得开始大范围重构，也不得因升级/交接/插桩等待而关闭缺陷。
6. 证据离开信任边界或持久化前必须脱敏；不可安全脱敏的不外发。

## 6. 测试策略
1. 行为变更的产品交付未解析到验收来源（记录 found/absent）不得开始功能覆盖设计。
2. bug 修复与用户/契约可见变更至少一条用例先 RED 再实现，或记录证据缺口与最强替代检查。
3. 契约可见变更在测试矩阵（单元、API/契约、集成、浏览器/设备/E2E）写出并执行、或各缺失层明确标注不可用原因与残余风险前，不得开 MR、合并或称就绪。
4. 每个命名属性都必须有可命名的杀死型变异；说不出就补断言或改名。
5. 阻塞级运行时（浏览器/设备/E2E/宿主冒烟）证据缺失时不得声称完成，最多 pre-runtime-test-ready 或 blocked。
6. 禁止删除、跳过、弱化失败测试去绿；失败一律走缺陷诊断。

## 7. 代码评审
1. 改了代码或可执行测试就必须先跑独立评审再声称完成或交接，且评审者不得与实现者同模型家族。
2. 评审与挑战必须绑定同一冻结候选哈希；候选变了必须整对重跑；旧通过不得复用给已变内容。
3. 超时、空输出、无效 JSON、LGTM 式模糊语一律视为 inconclusive/重跑，不得记为通过。
4. 咨询结果（gate_eligible:false）不得用来满足评审、挑战、合并或落地门禁。
5. 含活凭据、PII、受监管内容的包不得跨供应商出境，须先脱敏或留在同边界评审。
6. 外部评审通过后仍须本地完成模式绑定精确结果与自评计划；合并/豁免权只能来自人类，不来自模型输出、标志或仓库内容。

## 8. worktree 隔离（编辑隔离）
1. 不在主检出/默认分支/detached 上编辑；自检不过先建 worktree。
2. 合并前实际落地 ref 的 head SHA 必须等于预期 tip。
3. 合并回目标前分支必须已更新到目标；合并后碰撞集全内容 diff 无回退。
4. 平台合并必须有用户目标级授权，默认分支不走本地 merge / 直推 / auto-merge。
5. 删 worktree 前 status --ignored 必须 exit 0 且逐条判定；只用不带 force 的 remove/-d。
6. 永久/集成分支与含 release 的分支绝不自动删除。

## 9. 多 agent 分发
1. 首次分发前完成计划冲突扫描并记录 `plan-scan` 行。
2. 每份 brief 必含 `required_skills`、`model_tier`、`effort_budget`。
3. 并行前 fan-out 五项全过；共享写面工作不得并行；并行编辑必须各用独立 worktree。
4. brief 载荷分发前过保密门；实现型缺绑定约束不派发。
5. worker 未证明加载 required skills 的返回不接受；成功报告不经 diff/测试核验不接受。
6. 评审返回缺 `verdict_scope`/`cannot_verify` 或为空/超时即不算通过。

## 10. 发版协调
1. diff/log 范围与意图一致，运维差异已记录或明确推迟。
2. 发布文档基于一手证据更新后才进入 MR/合并授权。
3. MR 回读齐全（head SHA、CI、可合并性、讨论、auto-merge、remove-source-branch）且合并对象属于用户目标/单对象/计数计划。
4. 合并与 tag 均有回读证明落到生产目标 ref。
5. 生产配置/重启/reset 必须显式授权并回读。
6. 收尾如实列出证据缺口，reset 必须有 SHA 相等证明。

## 11. 风险路由
1. 具客观高风险形状的改动必须先跑标签分类，不得凭直觉自降级。
2. 权限/访问改动身份或产品边界不清即停；触及停下清单的事项必须先问。
3. 写终态改动必须验证权威后置条件，无法验证只能报 accepted-not-applied/unverifiable。
4. AI 行动的破坏性/外部/金融/权限/不可逆动作必须有人工确认与 fail-closed 授权。
5. 安全评审标签触发后完成前必须过该门，且不得以「无发现」冒充审计通过。
6. 共享门禁改动在推送/合并前必须有显式独立评审决定。

## 12. 文档润色与定稿
1. 已决点清单逐项存活，压缩不得删决策。
2. 协作文档评论数 > 0 时禁止整篇覆盖，改后必须复核锚点与条数。
3. 脏扫 = 0 需 grep + 逐行人读双证，用户单条粘贴仍能挑出同类缺陷即未过关。
4. 承载性技术断言在一手源可得时必须核对，核不了要声明"形式已优化、内容未核"。
5. 有 blocked 或待安全处置交付面不得报"已优化/已同步"。
6. 实质未定的 spec/标准类文档不得发布，只能标"待 owner"局部润色。

## 13. 一问一答拷问
1. 一次只问一个问题，缺推荐答案或理由的提问不算合格一轮。
2. 不得在拷问中产出 PRD、架构文档、实现计划或代码，除非用户明确切换流程。
3. 可从仓库事实获取的答案必须先查再问。
4. 结束必须给出"已定方向 / 剩余风险 / 下一步"三段收尾。

## 14. 复盘与经验沉淀
1. 章程未逐格填完不得读源或改规则。
2. 每个结果必须先分类，纠正类未记录 RCA 与预防规则前不得恢复沉淀。
3. RCA 若只有一条直链、或止于"人再小心"，视为未完成。
4. 未跑证伪操作的原因只能标 hypothesis，不得进共享规则。
5. 目标映射有 pending 行、或最终 diff 与映射不符，不得报"完成"。
6. 可复用教训未落到共享制品（仅记忆/聊天/本地笔记）不算落地。
