# 评审·发布·诊断·委派手册（展开）

展开 SKILL.md §1（诊断）、§3.6（独立评审）、§5（发布）、§7.4（委派）与合并协议。评审系统本身的接线细节（评审包字节规则、计划字段上限、轮次预算、客户端路由）不在本文件，见 `tooling.md`，仅在有该评审系统时读。

## 1. 评审何时触发、前置条件
- 只要产生实现 diff 或可执行测试变更，完成前自动进入独立评审，不等用户要求；只读调查、状态回答、纯设计不触发。
- 先恢复当前任务、真实 diff、范围与授权；实现或范围一变，前面的方案评审不能抵扣代码评审。
- 先做与改动成比例的实现者自评和受影响验证；质量检查失败先在范围内诊断修复并重跑，只把真正阻塞项上报。
- 改了具名测试属性要做"杀突变"走查；同一契约有两条实现路径要做差分等价检查并明示已知差异；某测试族不跑要记具体理由。
- 复用旧评审结果的条件：覆盖当前候选、满足 owner 门禁、评审者独立、深度达标，且记录了回执位置与候选标识（commit 或 diff 摘要）；HEAD 不能覆盖未提交改动，标识对不上就不能抵扣。
- 已加载技能、自评、计划中的命令、未结束的句柄、未验证的文字声明都不是评审证据；原生子 agent 结果只在 owner 门禁认可其独立性与证据时才算。
- 用户明确说跳过评审：记为 skipped 而非 passed，记录原话与范围，过期或无关的指令不算跳过；不要为已授权任务内的常规评审再要确认。
- 自检就绪后同一轮内立刻发起评审并等到终态；不能停在"下一步评审"、不能重复起进程、不能把超时/无效输出/鉴权失败报成通过。
- 评审要引用仓库自己跟踪的契约文件并记录；改动有意偏离某条规则时，在评审前的计划意图里写清是哪条、为什么。
- 收到"契约缺陷"类发现：要么在任务范围内修规则，要么保留安全行为并把规则报给 owner 待办；禁止悄悄放宽契约让同一改动通过。
- 评审通过不等于允许提交、推送、合并、发布或部署。

## 2. 发布：范围确认与 MR 合并授权
- 建生产 MR、请求合并授权、推生产 tag、跑生产部署任务前，用第一手源码控制证据确认实际范围：解析精确目标与来源 ref，动作前立即重新 fetch，比较 base...head 的 commit 日志、文件变更和高风险区的行级 diff。
- 分类用户可见能力变化与运维变化（配置/默认值、迁移、脚本、任务、worker、队列、依赖、外部集成、开关、手工步骤），并与用户意图和发布文档比对。
- 以下情况阻塞并要求用户重确认：来源含无关能力或范围明显过宽、选错分支/ref、目标在范围记录后推进改变了 diff 基线、运维类变更未写入发布文档、证据只到 commit/文件级却声称行级或运行时验证。
- 不从分支名、MR 标题、记忆、发布说明或他人模型摘要推断范围。
- 授权按用户表述的目标划界："完成并合并/发布这个版本"已覆盖为此目标必需的范围内合并（含后续新建的 PR），呈现具体 ref、范围与顺序是执行证据不是新的权限请求；不覆盖无关发布、保护规则修改、破坏性数据操作；"仅准备"和"停止"优先。
- 单独一句"合并"只覆盖讨论中的那一个 MR；"批量合并 N"限于计划内 N 个。
- 请求或执行授权前回读：URL/编号、源与目标 ref、当前 head SHA、CI 状态与链接、可合并/冲突状态、讨论与批准状态、自动合并标志。
- 目标/批量授权下范围内修复或新 PR 需要重新验证与评审而非重新授权；单对象授权下 head 变了要重新确认；第三方或越界改动要范围决定。
- 合并前重读变化的 CI、可合并性、目标 head、自动合并状态并解决失败门禁；未经用户对当前对象明确授权不开自动合并/合并队列/流水线通过即合并。
- 优先用能校验预期源 head SHA 的平台选项，否则动作前立即 fetch 校验并报告残余竞态；合并后回读合并状态、合并 commit 与目标分支 head。

## 3. 发布：tag、流水线、配置回读、收尾、重置、观察者
- 推生产 tag 前：解析合并后的精确目标 commit，确认本地与远端 tag 名不存在，确认目标是预期的生产 head，逐仓说明该 tag 会自动构建部署、产生手工任务还是什么都不做；不假设各仓 tag 规则相同。
- 推后回读：远端 tag 指向、tag 流水线存在或有记录的缺席、流水线/任务状态、需单独授权的手工任务、产出的镜像/摘要/版本。
- tag 指错不强移已发布的生产 tag，停下来交发布 owner 走修正版本路径。
- 版本指针不得低于已发布最高版本，且在合并时就检查而非只在打 tag 时；降版本通常来自无关改动里解错的冲突块；manifest 与 lockfile（可能多处）全部修齐；比较对象是发布记录（tag/registry）而非基线分支。
- 改生产配置/资源前：重读发布文档决定，先只读检查现状，只识别预期的 key/资源/工作负载增量，绝不打印 Secret 值，优先用 key 存在、值类别、哈希、修订或生效环境证明而非导出全部配置。
- 配置证据分四层：源 key 存在、部署/运行面收到、容器/进程有生效值或文件、应用行为/日志/指标证明已消费；多副本 API 与单例/专用 worker 分开回读副本数、镜像摘要、就绪与 key 存在。
- 未回读必需证据面不得说"发布完成"；收尾报告分：已完成（动作→回读证据）、等待/阻塞（对象/状态→下一动作或授权）、生产状态（tag、流水线、镜像、部署、配置、worker、冒烟/日志/指标）、有意未做（含残余风险）、需用户决定（精确对象与当前 id/SHA/状态）。
- 证据深度标签：read-back（平台/API/CLI 状态已查）、runtime-verified（运行中行为已查）、documented-only（只有文档说）、not-run（明确未执行）；部分证据只在诚实标注缺失面时可接受。
- 发布后重置集成环境分支是远端指针维护：先确认收尾足够作基线，列出目标 ref 与所有待重置分支，fetch 并记录前 SHA，优先先 dry-run，用带 lease 的强推把远端目标直接指到各环境分支，随后 fetch 并逐一比对；全部等于目标 SHA 才算完成；避免 checkout 后本地硬重置的脚本。
- 范围确认后产出测试范围提示（交接物，不是完整测试策略）：必须覆盖的能力、运维检查、回归重点、建议冒烟、是否需要完整测试策略交接及原因；覆盖能力/运维/风险（鉴权、隔离、数据变更、资金配额、异步终态、不可逆、高流量/降级）/回归（触及模块、直接消费者、相邻路径、历史失败、回滚敏感）/证据缺口五个维度；仅凭此提示不得标记发布验证完成。
- 观察者只为具名对象启动（MR、流水线、任务、部署、健康检查），记录 id/ref/SHA 与预期停止态，带超时与间隔轮询，成功/失败/取消/需人工/超时/对象被替换即停；观察者绝不跑任务、重试、合并、推 tag、改配置、删分支；敏感动作的完成声明要在主报告里用新鲜回读核对；超时报告最后观察状态与下一安全动作，不在主线程无限轮询。

## 4. 缺陷诊断
- 诊断视角：契约（字段、协议兼容、枚举默认、错误封装、映射）、状态（行、事务、缓存、锁、幂等记录、工作流状态）、时间（截止、重试、异步、租约、时区、竞态、最终一致）、依赖（下游状态、超时、畸形响应、凭据/配置不匹配）、运行时（环境、开关、动态配置、部署版本、生成文件漂移）、测试（无效夹具、过度 mock、缺清理、顺序依赖、依赖真实基础设施）、人/agent 流程（验收不清、跳过失败路径、未验证假设、缺交接）。
- 定位比复现和修复更贵，按失败形态选定位招式：有好坏 commit→commit 二分（用全部已知好点、仅证据限定时用路径、合并引入用首父、卡顿用交替术语）；失败输入/配置/数据集→输入折半缩减直到每块都必需；单跑过合跑挂且串行稳定复现→保序套件二分找最小污染子序列并修隔离而非受害测试；多组件链→安全可重跑时一次运行在每个边界记录脱敏元数据（id、大小、状态码、字段存在，绝不记原始体、头、密钥、PII），第一个输出错的边界拥有搜索；有通过的类比→枚举全部差异含执行路径差异；下游观察到错值→逆向追到"正确输入首次产出错误输出"的点；生产无法复现→告警→示例 trace→span 树→按 trace-id 查日志，按属性分组与基线比较。
- 假设日志逐条记：假设、只有它才会产生的预测、它为真时不可能出现的证伪观察（先收这个）、探针成本/风险/副作用、结果（拒绝/确认/仅提示）；安全是过滤器不是排序，越界探针先剔除，其余按单位成本排除的备选数排序，再按可能性与残余风险破平。
- 留意混杂因素（错的主机/凭据/网络位置）、主动探针副作用（加 CPU 改竞态时序、详细日志恶化延迟，下一探针前回滚）、只具提示性的探针（竞态、死锁）要标证据等级；换名重入被拒绝的假设类计入三振重评。
- 性能/资源/运行时症状按症状形态选工具而非团队熟悉度：CPU 热点→火焰图采样；I/O 卡住低 CPU→系统调用/动态追踪（注意开销与探针范围）；内存增长→堆分析；并发/死锁→竞态检测与全线程锁图（看所有线程不只断点那条）；UI 掉帧→帧级性能面板；网络延迟/丢包/TLS→抓两端的包；跨服务请求路径→先走分布式 trace，不要默认单服务分析器。
- 证据模板字段：症状、复现、失败命令/测试、环境/配置、缩窄的层、使用的定位招式、假设日志、做过并已回滚的主动测试改动、已证明的原因、复杂度判定（simple 要列查过且不存在的复杂触发项，complex 要说哪项触发及按视角的贡献因素）、修复、验证、回归测试、预防更新。
- 预防类型：契约（schema、校验、默认、必填、兼容测试）、数据（约束、事务边界、迁移检查、唯一键、保留策略）、运行时（超时、限流、熔断、锁租约、幂等、告警）、测试（回归、边界、契约、集成、回放、生成文件漂移）、评审（安全/数据完整/权限/并发/迁移/发布清单项）、工具（确定性生成器、非交互命令、更安全默认、覆盖保护）、规则（最小相关规则处的一句话）。
- 只有同时满足才更新共享规则：与产品无关、会改变未来行为、能写成短规则/清单项/步骤、有明确 owner；依赖单一业务或旧仓、已被覆盖、临时绕过、只增长不增效的一律不进。

## 5. 多 agent 委派
- 好任务的形状：一个目标、一个有界子系统/文件集/问题、明确的不动项与必保项、切片原样携带全局约束与相邻接口契约、模型档位字段、努力预算字段（工具调用/轮次/墙钟）、大输出写到持久产物并返回定位符加摘要（控制器从产物核验而非转述）、明确期望产出、验证命令或证据要求。
- 能力范围默认最小：只给任务需要的工具；默认拒绝再委派、与用户交互、写共享/持久记忆、跨系统副作用、范围外文件/git 写、装包/进程服务控制/环境配置改动、读密钥；这些都需单独显式授予。
- 只派本轮内能结束的工作；必须跨轮的用有 owner 与取消/清理的持久机制；被中断后确认子进程已终止并核对其写范围的残留副作用。
- 并行门（全部满足才并行）：任务可独立理解、写范围不相交或只读、共享准备稳定、无结果依赖、按上下文边界而非角色切片、共享隐式决定（命名、结果/错误形状、配置 key、依赖与风格）预先做好并写进每份简报、事后能整合验证；失败可能同根因、迁移/契约重叠、会改同一文件时不并行。
- 多 agent 是单 agent 3–10 倍 token 加协调成本：只在高价值、真正广度优先（多独立子任务、信息量超一个上下文、多表面）时用；执行类任务真正可并行的比开放调研少，共享状态/契约/顺序就是假广度；不确定就先一个聚焦 agent 或顺序委派；独立不通信的并行 agent 会放大错误，控制器必须逐一审核返回。
- 评审序列：规格符合（对照原需求/计划查漏项、语义变化、无依据假设；委派此判决时评审包必须含规格原文，返回要带判决范围与无法验证项，缺即不完整）→代码质量（正确、安全、数据完整、测试、可维护、集成风险）→证据（看 diff、跑聚焦测试、确认声称的生成文件/迁移/文档真的变了）。
- 交接式落地只用于工作者产出的 diff 或触及外部消费面（共享/生成产物、lockfile、契约、迁移）的 diff；控制器自己写的低/中风险改动留在原流程；风险不清交风险路由而非自评。
- 派发前定生命周期门：命名各 owner 与分支/worktree 边界；建可被落地评审者查看的持久交接清单（层级产物、评审通过记录、挑战通过记录、已验证候选、清理证明，缺必填项阻塞落地）；评审层级只能由 owner 表行或风险 owner 的具体产物授权，控制器不能通过改标签本地降级；定义工作者停止线，不让其推断推送/合并权限；并行写工作者要先有归属路径清单，共享生成物保持顺序。
- 工作者各自隔离 worktree 与具名分支，明确拥有的文件、只读契约、证明命令；返回紧凑报告（commit/diff、改动文件、跑过的测试、跳过项、调用的 owner）；返回 diff 越出清单即强制顺序整合与评审。
- 实现者自报不是评审证据；LLM 评审前先跑确定性门（干净状态、预期文件范围、生成物检查、测试、目标新鲜度、流水线存在/状态）；按落地候选批量评审而非每个小修；评审+挑战都要求时修完在更新候选上重跑两个镜头。
- 通过记录必须同时证明：命令成功、记录的候选 SHA 或未提交 diff 哈希等于当前、包装器输出匹配预先记录的干净通过标记、阻塞发现为空、改动文件集与候选一致且落地前重验；无预记录标记的包装器、退出码单独、自由文本、超时、部分、畸形输出都是不确定；含规格判决时还要记录提供给评审者的规格定位符与控制器自验的包外义务。
- 只落地已评审 ref：落地不可变的已评审 commit，或对可变合并同时记录源 SHA 守卫与合并后补丁等价证明（无意外差异），仅父/头相等不算，因为冲突解决会改内容；CI 定义与运行状态分开查，"无 CI"需该 ref 的平台产物证明并命名补偿验证。
- 清理：先同步目标检出，确认 HEAD 包含已评审 SHA 且补丁等价，再移除 worktree 并用安全删除（非强删）删本地分支；squash/rebase/cherry-pick 等重写模式要有非祖先证明，默认只删干净的 worktree、保留分支并如实报告；安全删除失败视为阻塞，不用强删把清理做成完成。
- 完成门：按声明做新鲜验证、读全输出与退出码、检查 VCS 意外改动、说明已验证与未验证。

## 6. 共享分支 rebase、合并额度、安全评审门
- 判据只有一条"分支是否已共享"：私有未推送分支可 rebase；已共享分支以 fetch 后立即保存的远端 OID 为基线，远端独有提交存在时并入而非 rebase；左右计数哪列是远端独有不能省略，读反会把规则倒过来覆盖别人提交。
- 只信本分支这一次 fetch 保存的 OID，之后再 fetch 也不换钉值；强推必须显式绑定该 OID 的 lease，裸 lease 用本地 tracking ref，后台/IDE fetch 会把它推进成"与远端现状比较"。
- 重写后 commit 哈希与评论锚点全变，旧评审线程、批准、可合并与 CI 状态都不再证明当前提交；工具把重写与发布合成一步时只能返回后逐层重验，全过前不合并。
- 机械合并额度：单独"合并"或"批量合并 N"或"完成并合并 #编号"生成额度，任何新消息清除单次/计数额度；编号形式只绑定当前远端仓与该编号、60 分钟内消费一次，"继续/状态"保留，"停止/不要合并/撤销"撤销，其他消息暂停且不可恢复；执行必须是单条显式编号、指定策略、关闭自动合并的直接合并命令。
- 安全评审门恰好一种状态：not-applicable（仅变更触发臂，记录"安全态势未变"并排除新增/改变的信任边界、不可信输入面、敏感汇点、鉴权语义、数据可见性、密钥处理、加固、修漏洞意图）、pending-dedicated-review（内联初筛和任何外部配方的上限）、passed（只能由具名安全 owner 或专业评审设置，模型判断与风险接受都不能）。
- 显式的审计/威胁建模/渗透请求永远不是 not-applicable，至少是 pending；风险 owner 可记录例外带 pending 上线，但门仍是 pending。
- 内联初筛只做只读的代码追踪与护栏检查，OWASP/STRIDE 只是提问镜头不是覆盖声明；绝不说"安全/审计通过/无发现即安全"。
- 本门绝不跑利用测试；真正的利用测试需单独路由并在当轮明确授权：目标环境、合成租户/账号/凭据、允许动作、非生产边界、无真实外部副作用、回滚/停止条件、责任 owner，缺一即停；生产或类生产凭据与变更永远无效。
- 安全门不降级其他风险标签或停止规则，与权限、外部集成、发布运维、AI 动作标签共存；假设不清先停下问；发现按 failure_path + impact + evidence + smallest_fix 规范化。
